﻿# 系统验证与模型接入方案

## 1. 目标

在正式建筑和单位模型未交付时，使用已有模型与显式标记的代理 prefab 验证建筑、单位、科技、弹道、位移、寻路和确定性回放。正式模型到位后只替换表现资源，不改变数据表路径、实体 prefab GUID、逻辑数值和权威碰撞规则。

本方案的完成标准不是“场景里能看到模型”，而是以下四层分别可验证：

- 数据与资源引用完整，缺失或结构错误立即报错。
- 核心战斗结果使用 Fix64 精确断言。
- 从 Launch 场景进入，由 procedure 加载验证关卡并走正式运行链路。
- 表现层的动画、出手点、拖尾和弹道与逻辑层解耦，可以单独替换和验收。

## 2. 实体表现结构

单位和建筑实体 prefab 必须使用稳定的实体壳。原始 FBX 只能存在于 `Display` 子树内，不能承载玩法脚本或权威碰撞。

```text
EntityRoot
├─ EntityPresentationBindings
├─ CharacterController（单位）
├─ HurtBox（单位）
├─ Display
│  └─ FBX 或嵌套表现 prefab
└─ PresentationSockets
   └─ ProjectileOrigin
```

约束如下：

- `Display` 必须是实体根节点的直接子节点，名称固定且只能有一个。
- 单位必须显式绑定 Animator，Animator Controller 必须包含 `Moving` Bool 和 `Attack` Trigger。
- 远程武器首次出手时必须存在 `ProjectileOrigin`，不允许使用固定高度或 Transform 搜索兜底。
- 安装 `WeaponAttackTrailEffect` 的实体必须显式绑定 `WeaponAnchor` 和 `TrailPoint`。
- `Display`、`SizeReferenceRenderer`、Animator 和挂点统一由 `EntityPresentationBindings` 保存，运行时不按名称猜测骨骼。
- 建筑 Animator 可为空；建筑出手时仍必须绑定 `ProjectileOrigin`。
- 代理 prefab 在绑定组件中标记 `Placeholder`，资源报告必须能列出，但代理本身不是错误。
- `Display` 子树只允许视觉组件，存在任何 `Collider` 都必须显式报错；玩法碰撞放在实体壳内、`Display` 外。
- 单位实体根缩放是表现资产基准，运行时禁止用逻辑碰撞半径缩放根节点或 `Display`。逻辑碰撞半径只同步到根节点 `CharacterController.radius`，视觉大小只在 `Display` 内由模型接入人员校准。
- 代理单位和通过新版 `FbxToPrefab` 接入的单位，`SizeReferenceRenderer` 水平包围半径 `max(bounds.x, bounds.z) / 2` 必须直接对齐 `CharacterDataDetail.Size` 对应的 `GameConfig` 碰撞半径（地块格，1 格 = 1 Unity 世界单位）。`SizeReferenceRenderer` 必须是代表身体主体的 `MeshRenderer` 或 `SkinnedMeshRenderer`，武器、拖尾、粒子和其他附件不得作为尺寸参考。只对 `Display` 做等比缩放，高度随模型比例自然变化，不修改配置、寻路 Agent 或 HurtBox。已有人工定标的非代理单位不由批量命令改写。

## 3. FBX 到 Prefab

`Tools/FbxToPrefab` 是模型接入的唯一标准入口。

### Unit

- 输出目录固定为 `Assets/AAAGame/Prefabs/Entity/Soldier`，与 `CharacterDataDetail.PrefabPath` 一致。
- 自动创建实体根、`Display`、`PresentationSockets`、`ProjectileOrigin`、CharacterController 和 HurtBox。
- Animator Controller 为必填项；工具把 FBX Avatar 绑定到实体根 Animator。
- Unit 模式必须选择 `Unit Size` 和 `Size Reference`；工具默认选择垂直尺寸最大的实体 Mesh，接入人员必须在预览中确认它是身体主体，然后按该 Renderer 的水平包围半径归一化到配置表中同体型的碰撞半径。
- 需要近战拖尾时显式开启拖尾绑定。Humanoid 使用右手骨骼；非 Humanoid 必须指定武器挂点路径，找不到时终止生成。
- 生成结束立即运行表现契约校验，校验失败时不保存不完整 prefab。

### Building

- 输出目录保持 `Assets/AAAGame/Prefabs/Entity/Building`。
- FBX 放入 `Display`，玩法 BoxCollider 保留在实体根子树。
- 当前模型尺寸未知的建筑使用已有建筑代理，不把代理 Mesh bounds 当成最终策划尺寸。
- 正式尺寸确认后重新烘焙逻辑障碍和战斗形状，并重跑建筑放置、寻路和攻击距离基线。

## 4. 代理资源

编辑器命令 `Tools/Entity Presentation/Generate Missing Proxy Prefabs` 扫描 `CharacterDataDetail.txt` 和 `BuildingTable.txt`：

- 只为不存在的配置路径创建 prefab。
- 单位复制已验证的单位实体壳，建筑复制已验证的建筑实体壳。
- 单位代理按 `CharacterDataDetail.Size` 自动校准 `SizeReferenceRenderer` 水平包围半径；现有代理可用 `Tools/Entity Presentation/Normalize Unit Visual Radii` 重跑同一校准。该命令只处理 `IsPlaceholder=true` 的单位，正式模型不会被批量改写。
- 保留每个配置路径独立的 prefab 和 GUID，之后可逐个替换正式模型。
- 生成后重新迁移绑定、烘焙建筑形状并输出完整报告。

不得把多个数据表路径运行时静默重定向到同一 fallback 资源。资源缺失必须在编辑器门禁或运行时明确失败。

## 5. 测试分层

### 5.1 资源契约

- 所有 `CharacterDataDetail.PrefabPath` 和 `BuildingTable` 等级路径必须存在。
- 所有实体壳必须通过 `EntityPresentationBindings` 校验。
- 建筑碰撞只允许由烘焙器支持的 BoxCollider 表达。
- 建筑战斗形状、逻辑障碍目录与实际 prefab 数量和路径完全一致。

### 5.2 纯逻辑测试

- 移动、伤害、科技、弹道和位移断言使用 `Fix64.RawValue`。
- 相同初始快照、输入、帧号和随机种子必须得到相同状态 Hash。
- 不以动画、Renderer、Unity 物理接触结果作为权威判断。

### 5.3 Launch 集成验证

验证关卡必须从 `Launch` 进入并由 procedure 加载，不允许直接打开测试场景宣称链路通过。验证区至少包括：

- 单位移动、转向、追击、拥挤和不同体型。
- 七种 WeaponType、移动目标、治疗、溅射、弹药和死亡。
- 推拉强度、重量抵抗、叠加、撞墙滑动和攻击锁定恢复。
- 建筑放置、旋转、升级、生产、阻路、失效和占领。
- 科技解锁前后、作用域、叠加、存量/新生单位与敌我隔离。

同一脚本场景分别在 30、60、144 渲染帧率执行，最终权威状态 Hash 必须一致。

建筑批量放置、升级、销毁等操作会使 Small、Medium、Large 导航 World 进入 runtime-dirty。切入 Invade 或 Defend 时，必须在生成敌人或启动敌人行为前原子完成全部 pending runtime-dirty rebuild；完成后记录 `phase.navigation-ready worlds=N`。任何 World 仍处于 pending、重建任务无法创建或导航管理器不存在时必须明确报错，不能让敌人继续使用旧流场。

Unity Editor Pause 不属于游戏内时间推进。恢复 Play 后必须重新设置逻辑时钟的 realtime 基准并保留既有 accumulator，禁止把暂停时长折算成待补逻辑帧。回归时至少暂停数秒，确认日志出现 `Editor pause ended. Rebased realtime without catch-up`，且恢复后的首个渲染帧没有大批 Catch-up。

### 5.4 失败证据

失败记录至少包含场景编号、逻辑帧、随机种子、LogicEntityId、输入命令、关键 Fix64 原始值、Buff/科技列表、弹道 ID、预期与实际状态以及回放 Hash。表现问题额外保存截图或录屏。禁止用增加等待时间、忽略空值或添加 fallback 让验证继续。

## 6. 正式模型替换流程

1. 使用 `FbxToPrefab` 生成或更新目标实体壳，并确认 `Size Reference` 指向身体主体而不是武器或特效。
2. 在预览中核对身体水平半径和整体视觉比例，不修改实体根变换。
3. 显式绑定 Animator、ProjectileOrigin、WeaponAnchor 和 TrailPoint。
4. 运行表现契约和数据表全量资源测试。
5. 运行该单位或建筑的 Launch 验证跑道。
6. 只有策划尺寸发生变化时才重新烘焙玩法形状并重跑相关逻辑基线。

## 7. 实施阶段

- 阶段 A：表现绑定组件、现有 prefab 迁移、FBX2Prefab Unit 流程。
- 阶段 B：缺失单位/建筑代理、数据引用和形状目录门禁。
- 阶段 C：弹道出手点和拖尾显式绑定，补充对应自动化测试。
- 阶段 D：Launch 验证关卡、脚本式场景和跨渲染帧率状态对比。
- 阶段 E：正式模型逐个替换，代理数量归零作为内容交付门禁。

## 8. 自动化入口与当前基线

日常资源接入按以下顺序执行：

1. 新 FBX 使用 `Tools/FbxToPrefab` 生成标准实体壳。
2. 数据表增加新路径后，执行 `Tools/Entity Presentation/Generate Missing Proxy Prefabs` 补齐代理并重烘焙形状目录。
3. 执行 `Tools/Entity Presentation/Validate Entity Prefabs`，确认所有实体结构和 Animator 契约通过。
4. 运行 EditMode 程序集 `AAAGame.Tests.Editor`，验证数据表引用、形状目录、Fix64 逻辑和错误路径。
5. 从菜单执行 `Tools/Validation/Run Launch System Validation`，等待 Unity 自动返回 Edit Mode。
6. 以 `Logs/SystemValidationResult.txt` 和 `Logs/LogicRuntimeLongSessionGateResult.txt` 为最终证据；两段结果必须同时为 `PASS`。

2026-08-01 完成实现时的基线如下：

- 单位 prefab 23 个，建筑 prefab 194 个，表现契约全部通过。
- 临时单位代理 16 个，临时建筑代理 138 个；正式模型替换后应逐步归零。
- `AAAGame.Tests.Editor` 为 678/678 通过。
- Launch 验证观察到单位视图 4、建筑视图 21、显式拖尾 2、逻辑弹道峰值 2、弹道视图峰值 8。
- 科技命令实际应用，三级击退目标实际位移；3000/3000 逻辑帧通过。
- 动态障碍为 0 时，仍验证 38 个静态烘焙阻挡形状全程无漂移，不能把静态烘焙建筑误判为缺少障碍。
- 雾效隐藏 Renderer 是合法运行时状态；结构门禁检查 Renderer 是否存在，运行报告单独记录 `visibilityHiddenViews`。

状态 Hash、实体 ID 和激活帧以每次报告为准，不复制为固定常量。跨运行比较必须使用相同初始快照、输入、随机种子和固定逻辑帧调度。

## 9. 2026-08-01 LvTest 现场回归

- `Buil_Def_Lv0` 使用现有 `ArmyLv0` 模型作为占位，交互 Collider 全部为 Trigger；正式防御建筑模型交付前不据此确定最终建筑尺寸。
- 默认远程武器的表现弹道从不存在的 `TestProjectile` 改为现有 `Projectile`。验证时必须同时观察逻辑弹道 ID、攻击次数和弹道 View，不能仅凭“没看到弹道”判定单位未攻击。
- 防御敌人的出生加速由 `defend_phase_speed_override` 表达；每个逻辑帧使用 Fix64 权威视野、按 LogicEntityId 排序检查，首次进入我方逻辑视野时移除。不得用 `Fog3Manager.Update()` 的表现可见事件驱动核心 Buff；日志必须出现 `Released spawn speed on authoritative visibility`。
- Medium 新单位异常偏大来自旧逻辑按 `逻辑半径 / prefab CharacterController.radius` 缩放整个实体根。现行合同只同步 `CharacterController.radius`，不改变实体根与 `Display` 缩放；运行回归需比较骑手、灭火员、英雄和剔骨狂魔的根缩放与 Renderer bounds。
- 英雄曾被错误缩小的直接原因是把完整 `Display` 当尺寸参考：完整水平半径为 `0.9554`，身体主体仅为 `0.4366`，右手武器和 `TrailRenderer` 撑大了 Bounds。现行合同只使用显式 `SizeReferenceRenderer`，完整 Display Bounds 不再参与单位尺寸归一化。
- 大量建筑后敌兵“有目标、移动状态和速度正常但位置不变”的根因是 runtime-dirty 导航重建尚未提交：建筑持续使进行中的任务失效重启，而战斗阶段过去未等待新 World 就绪，旧流场位移会被新建筑静态碰撞抵消。Editor Pause 后恢复时敌兵重新移动，是暂停期间 realtime 被补跑并顺带推进完导航重建造成的表象，不是 AI 自愈。
