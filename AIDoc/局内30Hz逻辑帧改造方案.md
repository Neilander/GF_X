# 局内 30Hz 确定性逻辑与可回放改造方案

## 0. 文档定位

本文档把当前“固定 30Hz 调度”继续推进为“输入逐 Tick、权威状态全定点、可记录并可重放”的局内确定性模拟。

当前工程已经具备 30Hz 逻辑帧时钟、追帧、逻辑与渲染更新拆分、Display 插值和脚本式物理推进。这些只能保证逻辑代码以固定频率被调用，不能保证同一输入在不同帧率、机器或运行中得到相同结果。

后续改造的最终标准是：

- 初始快照、内容版本、随机种子和逐帧命令相同时，所有受支持平台每个逻辑帧的权威状态 Hash 一致。
- 任意按键严格归属一个逻辑帧，只消费一次；连续输入在每个逻辑帧都有明确值。
- 逻辑时间由帧号和整数 Tick 表达，不依赖 float 秒数反复累计。
- 攻击、移动、寻路、单位避碰、墙体截断、动态障碍、投射物和命中判定都不读取 Unity 浮点物理结果作为权威结果。
- 渲染帧率、追帧次数、CPU 性能、异步资源完成时机、Unity InstanceID、字典遍历顺序和表现层随机数都不能改变逻辑结果。

本文档既是设计方案，也是迁移门禁。未达到对应阶段验收条件时，不能宣称已经支持确定性回放或 Lockstep。

## 1. 术语与确定性等级

### 1.1 术语

- 渲染帧：Unity Update、LateUpdate 和画面呈现所在的帧。
- 逻辑帧：固定 30Hz 的权威模拟 Tick。
- 权威状态：会影响未来游戏结果、必须进入状态 Hash 的数据；是否进入产品阶段检查点由独立白名单决定，不能把所有战斗瞬态都当成存档字段。
- 表现状态：Animator、粒子、音频、Display 插值等不允许反向影响逻辑的数据。
- 外部命令：玩家输入、关卡脚本命令、出生/销毁、GameSpeed 变化等模拟域外注入的数据。
- 稳定 ID：由逻辑层分配、跨运行一致的 EntityId、ObstacleId、JobId，不是 Unity GetInstanceID。
- 帧初快照：当前逻辑帧开始时所有权威实体状态的只读视图。
- 提交阶段：本帧所有意图和碰撞求解完成后，统一写入下一状态。

### 1.2 目标等级

本方案目标不是“同一台机器大概率一致”，而是：

1. 同一构建重复运行一致。
2. 不同渲染帧率和卡顿方式一致。
3. 不同异步资源冷热状态一致。
4. 不同受支持 CPU 和平台一致。
5. 开发/CI 的逐 Tick 确定性日志可定位首个分歧；产品恢复只承诺返回本局任一阶段开始时，不承诺任意 Tick 续跑。

### 1.3 不属于权威模拟的内容

- Animator 状态机采样。
- Display 子树插值。
- 粒子、拖尾、音频、镜头和 UI 动画。
- 调试绘制、性能统计和日志节流。
- 只用于显示的 Unity Collider 和 Rigidbody。

这些模块可以使用 float 和渲染时间，但不得修改权威位置、目标、伤害、导航或随机数状态。

## 2. 当前实现审计

| 子系统 | 当前实现 | 与目标的差距 | 风险 |
| --- | --- | --- | --- |
| 逻辑时钟 | 真实时间累积后按 30Hz 追帧 | FixedDeltaTime 使用现有 Q12 Fix64 的 1/30 截断值 | 中 |
| 输入 | Unity Update 覆盖 InputModel 标量和 bool | 没有 frameId、事件队列和逐 Tick 消费 | 极高 |
| 攻击 | WindUp、WindDown、Cooldown 分段 float 计时并清零 | 分段向上量化、余量丢失、周期多出 Tick | 高 |
| 寻路构建 | Flow world、runtime dirty、tile 按 Stopwatch 毫秒预算推进 | 完成帧受机器性能影响 | 极高 |
| Flow integration | float cost、float heap、部分平局无稳定二级键 | 跨平台和遍历顺序可能分叉 | 极高 |
| Crowd steering | Vector3/float，邻居与分离量按容器顺序累加 | 顺序和舍入影响最终速度 | 极高 |
| 单位更新 | 每个实体读取、计算、移动、立即提交 | 不是统一帧初快照，先后顺序影响结果 | 极高 |
| 墙体约束 | Flow 网格候选/滑动/7 次二分后再 CharacterController.Move | 两套几何裁决，Unity 结果成为权威 | 极高 |
| 单位碰撞 | Flow 软避让叠加 Prefab Layer 控制的 CharacterController 硬碰撞 | 不同兵种可能使用不同规则 | 极高 |
| 动态障碍 | 从 Collider world Bounds 注册 AABB 或圆 | 旋转、缩放、Y 高度会造成逻辑形状失真 | 高 |
| 实体与障碍 ID | 大量使用 GetInstanceID | 跨运行不稳定 | 极高 |
| 生命周期 | ShowEntity 和 Factory 资源加载完成后才具备组件 | 缓存冷热会改变开始参与逻辑的帧 | 极高 |
| 随机数 | UnityEngine.Random 与表现逻辑共用 | 音频或飘字可扰动战斗随机序列 | 高 |
| Ghost 碰撞 | 逻辑方法内部仍使用 Time.frameCount 节流 | 受渲染帧率影响 | 高 |
| 命中/投射物 | HitBox Trigger、Collider 和 float Projectile | Unity Physics 仍会改变伤害结果 | 极高 |

当前最危险的明确分叉源依次为：

1. Stopwatch 导航工作预算。
2. CharacterController 和 PhysX 参与权威位置裁决。
3. 输入没有逐 Tick 封包。
4. GetInstanceID、注册顺序和容器顺序参与平局决策。
5. 单位逐个立即提交，缺少统一快照。
6. 异步加载决定逻辑激活帧。
7. 全局 UnityEngine.Random 被逻辑和表现混用。

## 3. 权威边界

### 3.1 必须成为纯逻辑数据的状态

- 当前逻辑帧号。
- 稳定实体 ID、类型、阵营、存活状态。
- XZ 权威位置、速度、朝向、碰撞半径和移动模式。
- 如 Y 参与玩法，则包含定点高度、垂直速度、地面层和台阶状态。
- 当前导航目标、路径句柄、Flow job 进度、动态障碍版本。
- 目标列表、攻击序号、攻击起手帧、命中帧、后摇结束帧和下次可攻击帧。
- HP、Buff、技能 CD、弹药、确定性随机数流状态。
- 待提交的出生、销毁、伤害、治疗、位移和障碍命令。

### 3.2 禁止进入权威决策的数据

- Time.deltaTime、Time.time、Time.frameCount。
- Stopwatch、系统时间和每帧毫秒预算。
- Unity Transform 当前值作为逻辑源。
- CharacterController.Move 返回结果。
- Collider.ClosestPoint、Physics.Raycast、Trigger 回调作为伤害或阻挡的唯一判据。
- Unity GetInstanceID、Guid.NewGuid。
- 未排序的 Dictionary、HashSet 或对象注册顺序。
- UnityEngine.Random。
- 异步加载完成回调所在的渲染帧。
- Camera.main 和渲染摄像机朝向。

### 3.3 Unity 对象的定位

Unity GameObject 是权威实体的 View，不是实体本身。逻辑帧提交后，View 才读取 LogicTransform 更新根节点或 Display。

CharacterController 在最终架构中不能修正 LogicTransform。过渡期可以双跑并记录差异，但只能有一个权威结果。

### 3.4 调度器保留与修正

现有 LogicFrameClock 的真实时间累积和无丢帧追帧可以保留，但需要补齐以下语义：

- 逻辑时间以 frameId 为权威，一秒是 30 个 Tick；业务计时不再依赖 FixedDeltaTime 累加。
- Clock 必须为每个待执行 Tick 提供对应的真实时间截止点，供输入事件归帧。
- 一个渲染帧追多个 Tick 时，按各 Tick 截止点依次 SealInput、Tick，不能先把所有输入折叠成一份。
- GameSpeed 变化必须作为带 EffectiveFrame 的外部命令；Clock 保存速度时间段，保证输入时间戳仍能映射到唯一 Tick。
- 有 PauseToken 时不增加逻辑帧；暂停期间的真实时间和输入处理遵循第 5 节规则。
- 不设置丢 Tick 上限。watchdog 可以暂停并报错，但不能跳过历史 Tick。
- 追帧次数、backlog 和插值只属于调度/表现数据，不进入权威状态。
- Physics.Simulate 使用的 float 步长在迁移期只服务旧物理；最终权威逻辑不读取其结果。

Clock 的边界数学、Input System 时间戳时钟域和 GameSpeed 分段需要独立测试。尤其要覆盖事件时间恰好等于 Tick 边界、长暂停、速度切换和一次追帧数百 Tick。

### 3.5 全局逻辑倍率与子弹时间

子弹时间采用“改变 Tick 产生速度，不改变单 Tick 步长”的模型。

例如全局倍率为 0.2：

- 渲染仍按设备正常帧率运行。
- 逻辑 Tick 仍代表固定的 1/30 游戏秒。
- 每个真实秒只产生约 6 个逻辑 Tick。
- AI、攻击、Buff、导航、移动、碰撞和投射物自然一起减速。
- 碰撞 substep、攻击 Deadline 和所有 TickCount 不需要改成可变 deltaTime。

调度器使用：

    scaledAccumulator += realDelta * EffectiveSimulationRateScale
    while scaledAccumulator >= oneLogicTick:
        SealInput(frameCutoff)
        Tick()
        scaledAccumulator -= oneLogicTick

禁止用以下方式实现子弹时间：

- 保持每秒 30 Tick，但给业务传入 deltaTime * scale。
- 修改 Time.timeScale 让整个 Unity 更新链减速。
- 在每个组件内部自行乘 BulletTimeScale。
- 子弹时间开始时重算现有攻击、Buff 或导航 Deadline。

普通倍速、子弹时间和暂停合并到 LogicTimeControlService 管理，但暂停不是 0 倍子弹时间：

- BasePlaybackScale：普通倍速或 GameSpeed。
- BulletTimeScale：子弹时间倍率。
- PauseTokenSet：菜单、教程、系统弹窗等来源持有的暂停 Token。
- 未暂停时 EffectiveSimulationRateScale = BasePlaybackScale * BulletTimeScale。
- PauseTokenSet 非空时调度器不产出 Tick，AnimationRatePresenter 发布 0 动画倍率。

倍率使用确定性定点值或有理数，不使用业务 float。转成 double 只允许发生在 LogicFrameClock 的真实时间调度边界。

倍率变化通过带 EffectiveFrame、SourceId、Sequence 的 TimeScaleCommand 提交：

- 本 Tick 内触发的子弹时间在约定的 Tick 边界生效，不能修改已经执行一半的 Tick。
- 倍率变化只作用于之后到来的真实时间，不能追溯缩放已有 backlog。
- 当前倍率、活跃效果、来源 ID 和结束规则进入快照、回放与 StateHash。
- 外层真实时间、accumulator 和渲染插值 alpha 不属于权威状态。

多个子弹时间来源默认采用“最强减速生效”，即取最小 BulletTimeScale；不默认相乘，避免两个 0.2 效果意外变成 0.04。若以后需要叠乘，必须提升协议版本并定义稳定 SourceId 排序、上下限和取整规则。

子弹时间倍率必须大于 0。倍率为 0 会让逻辑 Tick 停止，逻辑 Tick 计时的效果永远无法自行结束。

暂停与恢复使用 PauseControlCommand 和独立控制通道：

- PauseControlCommand 在两个逻辑 Tick 之间生效，不能中断执行到一半的 Tick。
- 暂停后没有逻辑 Tick，因此 Resume 不能放在普通 LogicCommand 队列里等待 Tick 消费。
- RuntimeProcedureBase 在暂停期间仍处理外部时间控制通道、UI 和输入状态。
- PauseToken 按稳定 SourceId 管理；只有 Token 集合清空才恢复，避免关闭菜单时误解除教程或系统暂停。
- 暂停期间持续刷新 lastRealtime，但不增加 scaled accumulator，因此恢复时不追算暂停期间。
- 暂停时保留已有 accumulator 余量和插值姿态，恢复后继续；不能清零造成额外输入延迟或 Display 跳变。
- 进入暂停时生成 InputReset，暂停期间 Gameplay 输入不进入后续逻辑帧。
- 暂停期间 LogicTicks 类型的子弹时间剩余时长冻结，恢复后继续。
- RealTime 类型的子弹时间可以在暂停期间收到外部 EndTimeScaleCommand；该命令必须被记录，并在恢复前得到确定结果。

回放的权威逻辑只关心 Pause 生效和恢复时对应的逻辑帧/外部序列。若要复现“暂停菜单停留了多少真实秒”，作为非权威表现时间单独记录，不能进入 gameplay Hash。

效果持续时间必须显式选择时间域：

- LogicTicks：持续 N 个游戏 Tick；在 0.2 倍率下真实持续时间扩大 5 倍。
- RealTime：由模拟域外的单调时钟决定结束，并转换为带 EffectiveFrame 的 EndTimeScaleCommand；录制和联网时必须记录该命令。

不能在逻辑组件里读取 Time.unscaledTime 来结束效果。

### 3.6 动画和渲染语义

渲染帧率不因子弹时间改变，Time.timeScale 保持 1。

所有 gameplay Animator 通过统一 Presenter 应用：

    effectiveAnimatorSpeed =
        baseAnimatorSpeed
        * perEntityAnimationScale
        * EffectiveSimulationRateScale

约束如下：

- 不能由不同 Buff、武器或子弹时间代码直接互相覆盖 Animator.speed。
- 每个来源保存独立倍率，由 Presenter 每渲染帧或倍率变化时统一合成。
- 新创建或对象池复用的 View 必须立即应用当前倍率；Hide/Release 时恢复基准值。
- Animator Trigger 仍由逻辑事件触发，动画事件不得反向造成伤害或修改攻击 Deadline。
- 权威实体禁止 Root Motion；模型位移只能来自 LogicTransform 插值。
- UI、输入、摄像机和普通渲染保持正常速度。
- 粒子、拖尾和音频 Pitch 是否跟随子弹时间属于表现配置，不得影响权威状态。

Display 插值继续使用 scaled accumulator 产生的 alpha。倍率降低后，两个逻辑姿态之间会跨越更多渲染帧，Display 平滑地更慢移动；倍率切换时不能清空 accumulator，否则会产生位置跳变或额外 Tick。

## 4. 逻辑帧总管线

最终不能继续让每个 EntityBase 独立完成“读邻居、改自己、移动并提交”。需要由 DeterministicWorld 统一编排：

1. SealInput：封存本帧 LogicInputFrame 和外部命令。
2. ApplyLifecycleCommands：按稳定 ID 应用本帧出生、销毁、阵营和动态障碍命令。
3. AdvanceDeterministicJobs：按固定工作量推进 Flow world、runtime dirty 和 tile job。
4. BuildFrameSnapshot：按 StableEntityId 生成不可变帧初快照和空间索引。
5. EvaluateBrainAndTargeting：只读快照，生成目标和行为意图。
6. AdvanceAttackTimelines：按绝对截止帧生成命中、完成和打断事件。
7. BuildMoveIntents：手动移动、Flow 方向、击退和特殊移动统一产生 DesiredVelocity。
8. SolveStaticCollision：对静态网格和动态障碍做定点 swept-circle 与墙面滑动。
9. SolveAgentCollision：按稳定 PairKey 处理单位间约束和重叠恢复。
10. CommitTransforms：统一提交所有实体的新位置、速度和移动状态。
11. CommitCombatEvents：按稳定事件键提交伤害、治疗、Buff 和死亡。
12. FinalizeLifecycle：把本帧新产生的出生/销毁命令排到规定帧。
13. ComputeStateHash：对规范化权威状态计算 Hash。
14. PublishViewSnapshot：生成只读表现快照。

### 4.1 顺序语义必须固定

- AI、索敌、攻击距离默认读取帧初位置。
- 同一帧产生的移动不会反向改变本帧攻击是否命中。
- 同一帧开始时存活并成功产生攻击事件的单位，即使本帧同时死亡，是否仍可造成伤害必须全局统一。建议采用“帧初存活即可完成已到期命中”的同步结算规则。
- 同一帧多次伤害按 EventKey 排序提交，不能依赖攻击者遍历顺序。
- 新出生实体默认从下一逻辑帧参与 AI、攻击和移动。

这些规则一旦进入回放格式，后续修改必须提升回放协议版本。

## 5. 逐 Tick 输入

### 5.1 三层结构

输入拆为三层：

1. RawInputEventQueue：渲染域捕获 Input System 事件，永不直接覆盖逻辑 bool。
2. LogicInputFrame：属于唯一 frameId 的不可变输入快照。
3. LogicCommand：由输入帧解释出的移动、技能、交互和选点命令。

建议的数据字段：

- FrameId。
- PlayerId。
- 定点世界移动向量。
- HeldBits、PressedBits、ReleasedBits。
- 对可能一帧多次触发的操作保存 PressCount 或有序事件列表。
- 选点世界坐标或稳定目标 ID。
- 本帧输入 Sequence 范围。
- 校验码。

### 5.2 输入归帧

- 使用 Input System 事件时间戳和逻辑时钟时间段，将事件分配到尚未封存的目标 Tick。
- InputManager 只入队，不再使用 WasPressedThisFrame 覆盖 InputModel。
- 每个逻辑 Tick 开始前封存对应输入帧；封存后不可修改。
- 无新轴输入时延续上一 Tick 的 held/axis 状态；Pressed 和 Released 默认清零。
- 暂停期间的 Gameplay 输入默认丢弃，并在恢复时重采 held 状态，避免暂停期间的按键延迟爆发。
- 迟到且目标帧已经执行的本地输入不能静默塞入当前帧，应记录 LateInput 并按明确策略处理；非回滚模式建议放入下一未封存帧。

### 5.3 相机相对移动

模拟域不能读取 Camera.main。

输入适配层可以读取相机朝向，把摇杆转换为世界 XZ 方向后量化，并将量化后的世界方向写入 LogicInputFrame。回放只读取记录值，不重新读取相机。

### 5.4 输入不变量

- 每个 frameId、playerId 只有一个 LogicInputFrame。
- 每个 Pressed 事件只属于一个逻辑帧，只消费一次。
- 单渲染帧补 N 个 Tick 时，N 个 Tick 各读取自己的输入帧。
- 无逻辑 Tick 的渲染帧不能丢失按键边沿。
- 回放模式完全禁用真实输入读取。

### 5.5 高风险测试

- 120fps 下在两个逻辑 Tick 之间按下并释放，下一 Tick 必须收到一次 Pressed。
- 15fps 下单渲染帧补两个 Tick，Pressed 只能出现在指定 Tick。
- 500ms 卡顿期间产生多个输入事件，恢复后按时间顺序分配，不能合并或重复。
- 暂停期间按键，恢复后不得意外触发。
- 同一 Tick 内按下、释放、再次按下，事件次序和 PressCount 正确。
- 相同输入日志在无摄像机对象的 Headless 模拟中可重放。
- 子弹时间拉长一个 Tick 的真实时间区间时，区间内所有按键边沿仍保留并归属唯一 Tick。
- 倍率切换前后的输入 cutoff 使用同一条分段时间线，不能整体偏移一帧。

英雄普通攻击不依赖攻击键。PlayerAttack 可以保留为未使用字段以兼容旧资源，但不得影响自动普攻状态机。

## 6. 时间表达与攻击时间线

### 6.1 时间改为整数 Tick

权威计时器不再反复累加 FixedDeltaTime。使用当前帧号和绝对截止帧：

- LogicTime = CurrentFrame。
- Duration = integer TickCount。
- Deadline = StartFrame + TickCount。

这样一秒严格等于 30 Tick，不受现有 Q12 Fix64 无法精确表示 1/30 的影响。

### 6.2 内容迁移

运行时不应从 float/Fix64 秒数临时换算 Tick。增加内容迁移工具：

- 读取旧 WindUp、WindDown、Interval、BuffDuration 和 SkillCooldown。
- 按明确的最近 Tick 规则生成整数 Tick。
- 输出旧秒数、新 Tick 数和误差报告。
- 对误差超过阈值的配置要求人工确认。
- 最终 ScriptableObject 和表格保存 TickCount，秒数只用于 Inspector 显示。

常见配置应映射为：

- 0.3 秒 = 9 Tick。
- 0.5 秒 = 15 Tick。
- 1 秒 = 30 Tick。

### 6.3 单一攻击时间线

一次攻击起手时生成不可变 AttackSchedule：

- AttackSequence。
- StartFrame。
- HitFrame = StartFrame + WindUpTicks。
- RecoveryEndFrame = StartFrame + WindUpTicks + WindDownTicks。
- ReadyFrame = StartFrame + IntervalTicks。
- LockedTargetIds，按稳定 ID 排序。
- 本次攻击使用的武器类型和需要快照的配置。

攻击阶段只是根据当前帧和这些边界派生出来的显示状态，不保存三个独立 timer。

每 Tick 必须处理所有已跨过且尚未触发的边界。不能在命中、后摇结束或冷却结束时把 elapsed 清零。

对于自动攻击：

- CurrentFrame 到达 ReadyFrame 时，同一 Tick 即可安排下一次攻击。
- 如果不允许攻击重叠，则下一次起手帧为 max(ReadyFrame, RecoveryEndFrame)。
- MoveAtkComp 在 WindUp/WindDown 不产生移动锁。
- DirectAtkComp 在 StartFrame 到 RecoveryEndFrame 之间产生移动锁。

### 6.4 必须明确的战斗语义

- 目标在起手后离开射程，近战是否仍命中。
- 目标在命中帧死亡或不可选，是否消耗弹药。
- WindUp 或 Interval 在攻击中途被 Buff 修改，是影响当前攻击还是下一次攻击。
- 伤害值在起手快照还是命中帧读取。
- 多目标和弹药不足时的稳定目标顺序。
- 同一 Tick 的打断和命中谁优先。

建议规则：

- 时序参数在起手时快照，只影响下一次攻击。
- 伤害属性在命中帧读取帧初快照。
- 目标必须在命中帧仍存活且满足武器目标规则；是否重验射程由武器类型配置。
- 打断优先级高于尚未提交的命中事件。
- 多目标按 StableEntityId 排序。

### 6.5 攻击不变量与测试

- 两次起手间隔只由 ReadyFrame 规则决定，不受阶段数量影响。
- 0 Tick 阶段可以在起手 Tick 触发，不得强制额外占一帧。
- 攻击打断必须撤销尚未提交的事件，但不能重复恢复移动。
- 同一 AttackSequence 的命中事件至多提交一次。
- 0.3/0.3/1.0 配置的两次起手严格相隔 30 Tick，而不是 34 Tick。
- 对 0、1、8、9、10、29、30、31 Tick 边界分别测试。
- Buff 在 HitFrame 前后生效、目标同帧死亡、同帧打断、弹药耗尽都要有固定期望。

### 6.6 子弹时间中的攻击语义

AttackSchedule 使用绝对逻辑帧，因此子弹时间开始或结束时不修改 HitFrame、RecoveryEndFrame 和 ReadyFrame。

当倍率从 1 变为 0.2：

- 还差 6 Tick 命中的攻击仍然差 6 Tick。
- 这 6 Tick 在真实时间上变为原来的 5 倍。
- 动画 Presenter 同时把对应 Animator 的有效速度乘 0.2。
- 回到 1 倍后继续等待剩余 Tick，不做补偿或追帧。

这样逻辑攻击阶段和动画播放速度使用同一全局倍率，但 gameplay 命中仍只由 AttackSchedule 决定。动画归一化时间存在表现误差时不能调整命中帧。

若未来某个技能明确要求“不受子弹时间影响”，必须作为独立的 Unscaled 外部时间域设计，不能在普通攻击或通用 Buff 中偷偷除以倍率。

## 7. 定点导航世界

### 7.1 单一权威几何源

运行时导航继续使用 authored FlowNavigationGridAsset，但必须把权威数据标准化为：

- 整数 Width、Height、SectorSize。
- 定点 Origin、CellSize 和 CellAnchor。
- bool/bitset WalkableMask。
- byte 或整数 CostField。
- 固定顺序 NeighborTraversalMask。
- 稳定 PortalId 和 SectorId。

Unity NavMesh 不进入运行时权威链。

### 7.2 确定性 Flow 构建

必须移除所有基于 Stopwatch 的截止条件。每个逻辑 Tick 按固定工作量推进，例如：

- 最多处理 N 个障碍格。
- 最多执行 N 次 heap pop。
- 最多扩展 N 个 integration cell。
- 最多提交 N 个 tile phase step。

不同 CPU 只影响渲染耗时，不影响 job 在哪个逻辑帧完成。

所有 job 队列按稳定 JobKey 排序：

- WorldVersion。
- AgentTypeId。
- GoalCellIndex。
- SectorId。
- TileKey。
- EnqueueSequence。

优先队列比较必须使用复合键：

1. IntegrationCost。
2. CellIndex。

禁止只比较 float cost。缓存淘汰也必须有稳定二级键，不能依赖 Dictionary 枚举顺序。

### 7.3 同步构建入口

实体移动调用链中禁止 allowSynchronousBuild。否则调用实体的先后顺序会决定某个 job 在本帧是否完成。

需要立即可用的关键世界和初始 Flow 应在时间线启动前预热完成。运行期新请求没有结果时只能：

- 使用明确的确定性 pending 策略。
- 或保持停止，等待 job 在固定工作量下完成。

不能根据当前 CPU 剩余时间临时同步完成。

### 7.4 定点 steering

- DesiredDirection、DesiredVelocity、AgentPosition、Radius 全部使用逻辑定点类型。
- 邻居列表按 StableEntityId 排序。
- 分离力、TTC、Dot、Sqrt 和 Clamp 使用审计过的定点实现。
- 完全重叠时使用 StableEntityId 的确定性方向，不使用 InstanceID hash。
- steering 预测步长等于一个逻辑 Tick，不允许把 0.033 秒硬抬为 0.05 秒。
- 手动英雄可以跳过 Flow 方向，但不能跳过统一静态碰撞和单位碰撞求解。

### 7.5 数值类型

不能直接假设现有 Fix64 适合所有导航运算。实施前必须完成范围审计：

- 最大地图坐标。
- 最大速度、击退和单 Tick 位移。
- 距离平方、Cost 累加、乘除法中间值。
- Sqrt、Normalize 和除零边界。
- 运行 10 万 Tick 后的累计误差。

现有实现已经发现具体缺陷：

- float 减 Fix64 的运算符错误地执行了加法。
- FixVector3.Equals 检查了 FixVector2 类型，类型判断和强制转换互相矛盾。
- 定点乘法直接执行 raw 乘 raw，没有宽乘、溢出检查或统一饱和策略。
- 正负数转换采用有偏取整，适合部分玩法保守值，但不能未经审计复用于向量、法线和积分。

因此数值库是独立 P0 前置任务，不允许“边迁导航边顺手修”：

1. 选择修复现有 Fix64 或引入隔离的 DetFix/LogicScalar。
2. 明确 raw 格式、取整模式、溢出策略和除零策略。
3. 为加减乘除、比较、转换、Sqrt、Normalize、Dot、距离和向量相等建立黄金测试。
4. 使用随机属性测试验证交换律适用范围、单调性、归一化误差和边界溢出。
5. 在 Windows Mono、IL2CPP 和目标平台验证 raw 结果一致。

建议将时间完全改为整数 Tick；位置和速度使用独立的 LogicScalar。只有数值门禁通过后，才能迁移权威位置、Flow integration 和碰撞。

## 8. 帧初快照与单位避碰

### 8.1 读写分离

当前每个单位会在自己的 Tick 内立即更新 Transform 和 Agent position，后执行单位可能看到先执行单位的新位置。

目标结构必须是：

1. 复制或引用本帧只读 AgentSnapshot。
2. 用同一份快照为所有单位计算 MoveIntent。
3. 构建稳定排序的 AgentPair。
4. 统一求解碰撞。
5. 一次性 Commit。

### 8.2 空间索引

- 空间桶根据帧初快照一次构建。
- BucketKey 使用整数网格坐标。
- 桶内 AgentId 排序。
- 本帧 Commit 前不得失效或重建。
- 查询结果按距离、StableEntityId 明确排序；需要累加时至少按 StableEntityId 排序。

### 8.3 单位碰撞模型

建议权威 XZ 碰撞体统一为圆：

- Center = LogicPositionXZ。
- Radius = 逻辑属性 CollisionRadius。
- CollisionMask、Ghost、阵营穿透等是逻辑字段。

第一版 hard collision 建议使用“固定 substep + Jacobi 位置约束”：

1. 按固定 substep 数拆分本 Tick 位移。
2. 每个 substep 先对全部单位执行静态墙 sweep。
3. 从同一 substep 快照计算全部 Pair correction。
4. Pair correction 只累加到每个实体，不在遍历 Pair 时立即改位置。
5. 全部 Pair 计算完成后一次性应用修正。
6. 对修正后位置再次执行墙体投影。
7. 固定迭代 K 次，禁止按墙钟或容器顺序提前结束。

这种 Jacobi 方式避免“前一个 Pair 已改位置，后一个 Pair 读到新位置”的顺序泄漏。

碰撞约束必须满足：

- PairKey = min(EntityId), max(EntityId)。
- Pair 按 PairKey 排序。
- 固定迭代次数。
- 平分修正或按明确质量/优先级分配。
- 完全重叠时按 PairKey 产生固定法线。
- 每次迭代使用同一规则，不提前因耗时退出。
- 单位 Pair 修正后必须重新投影静态墙和动态障碍约束，防止“解决人碰人”时把单位推进墙内。
- 静态约束与单位约束的交替次数固定，不能检测到看似稳定就因容器顺序提前退出。
- 等质量单位严格各承担一半修正；不可移动单位使用 inverseMass = 0。
- 完全同位时法线由 Stable PairKey 映射，不能归一化零向量。
- 配置必须满足 maxSpeed * tickDuration / substepCount 不大于最小碰撞半径的一半；超限击退需要额外 swept-disc TOI，不能静默穿越。
- 固定 K 次后残余穿透超过 epsilon 时，开发和 CI 必须 fail-fast，不能交给 PhysX 兜底。

### 8.4 容易出 Bug 的语义

- 一方不可移动时，另一方承担全部修正。
- 双方都不可移动时记录重叠，但不产生 NaN。
- Ghost 与普通单位的 mask 必须在逻辑帧立即生效，不再用 Time.frameCount 每 6 个渲染帧同步。
- 目标单位可以允许更小的战斗接近距离，但不能让碰撞半径和攻击距离相互打架。
- 对象池复用必须清空上一生命周期的速度、重叠、Ghost 和 collision mask。
- Prefab Layer 不得改变权威单位碰撞规则。

## 9. 静态墙体与位移截断

### 9.1 权威结果

每个单位本帧只有一个 ProposedDisplacement，经过逻辑碰撞得到 ResolvedDisplacement：

    proposed = desiredVelocityPerTick + externalMovePerTick
    resolved = SolveStaticWorld(position, radius, proposed)
    resolved = SolveAgentPairs(snapshot, resolved)
    nextPosition = position + resolved

CharacterController.Move 不再修改 nextPosition。

### 9.2 静态碰撞算法

最低可接受过渡方案：

- 将现有线段采样、DDA 穿格、墙面切线和最长前缀全部改为定点。
- 采样顺序、边界法线顺序和二分次数固定。
- 平局按命中格和 CandidateIndex 决胜。
- 输出碰撞法线、命中格、截断比例和滑动次数。

最终推荐方案：

- 对膨胀后的阻挡格或定点障碍执行 swept-circle。
- 计算最早碰撞 TOI。
- 移动到接触点后投影剩余位移到墙面切线。
- 固定最大碰撞/滑动迭代次数。
- 多面同时命中时按 TOI、CellIndex、NormalAxis 排序。

现有 15° 到 75° 的方向扇候选应归属于 steering，不属于 collision。碰撞求解器只能截短给定的 ProposedDisplacement 或把剩余位移投影到接触切线，不能凭空选择一个新的绕行方向。否则墙角、窄门和对称障碍会把路径选择与碰撞响应混在一起，产生难以重放和难以调试的左右跳变。

### 9.3 边界语义

- 起点在合法区：不能穿入阻挡区。
- 起点已在阻挡区：只能沿能减少穿透的方向移动。
- 高速位移不能越过一个薄墙格。
- 角落同时撞两面墙时不能因 X/Z 比较微差随机选择不同方向。
- 小于最小位移的截断不能让 IsMoving 保持 true。
- 实际移动状态必须根据 ResolvedDisplacement，而不是 DesiredVelocity。
- CollisionRadius 改变后必须在同一 Tick 更新空间索引和墙体 clearance。

### 9.4 碰撞不变量

- 每个 Tick 每个实体的权威位置只提交一次。
- 从合法位置出发的整段 swept trajectory 合法，不能只验证终点。
- Broadphase 必须包含所有本 Tick 可能接触的 swept pair，Pair 不重不漏。
- ProposedDisplacement 为零且没有重叠恢复时，位置不能自发变化。
- 静态碰撞只能缩短位移或沿接触切线滑动，不能增加位移能量。
- 单位 Pair 修正按规则成对守恒；不可移动单位和墙体除外。
- 提交后墙体穿透和单位穿透均小于规定的 raw epsilon。
- 所有并列 TOI、法线、Pair 和候选都有稳定完整的平局键。
- 任意 NaN、除零、定点溢出和无法恢复的深穿透必须 fail-fast，并输出最小复现场景。

### 9.5 Y、高度和坡度

当前 CharacterController 隐式处理重力、isGrounded、SlopeLimit 和 StepOffset。移除其权威地位前必须明确 2.5D 规则：

- 若玩法只权威 XZ：Y 从 authored cell anchor 或高度图确定，只做表现贴地。
- 若击飞、台阶和坡度影响玩法：增加定点 Y、垂直速度、地面高度、最大坡度和步高规则。

不能在 XZ 定点化后继续用 CharacterController.isGrounded 修改逻辑垂直状态。

## 10. 动态障碍与建筑

### 10.1 逻辑障碍命令

建筑和临时障碍必须通过 LogicObstacleCommand 进入模拟：

- EffectiveFrame。
- StableObstacleId。
- AgentTypeMask。
- ShapeType。
- 定点 Center、Radius 或 HalfExtents。
- Rotation 若被支持，必须使用定点离散角。
- Add、Update、Remove。

Collider Bounds 只能用于 Editor 校验，不可在运行时生成权威形状。

### 10.2 当前形状失真风险

- 旋转 BoxCollider 当前按世界 AABB 注册，会扩大阻挡范围。
- 非 BoxCollider 当前按 Bounds.extents.magnitude 注册圆，Y 高度也进入 XZ 半径，高物体会被严重放大。
- Collider 缩放、子节点启用顺序和对象池状态可能改变注册结果。

### 10.3 增删一致性

- Add 在 EffectiveFrame 立即进入碰撞 overlay，不能等 Flow rebuild 完成后才阻挡。
- Remove 在 EffectiveFrame 立即从权威碰撞 overlay 删除，不能继续被旧 committed mask 阻挡。
- Flow tile 可以在固定工作量下逐步重建，但本地静态碰撞始终读取最新 WorldVersion 和 overlay。
- 一个逻辑 Tick 内只能查询一个不可变 CommittedNavigationWorld；WorkingWorld 完成后只能在 Tick 边界原子切换。
- 旧 WorldVersion 的路径、tile、缓存和预约不能继续写入新世界。
- 同一帧多个障碍命令按 StableObstacleId 和 CommandSequence 排序。

### 10.4 动态障碍测试

- 旋转建筑、非均匀缩放和高 Collider 不改变逻辑形状。
- 单位脚下添加障碍后只能向外恢复。
- 删除障碍的同一 Tick 即可通过局部碰撞，Flow 重建完成前采用确定性 pending 导航。
- 同一帧添加与删除同一 ID 按 Sequence 得到唯一结果。
- 障碍重建在快慢机器上完成于同一逻辑帧。

## 11. 稳定 ID、生命周期和随机数

### 11.1 稳定 ID

- EntityId 由逻辑世界分配或由 SpawnCommand 明确携带。
- ObstacleId、ProjectileId、AttackEventId 和 NavigationJobId 都从稳定数据派生。
- 对象池复用不复用逻辑 ID，除非回放协议明确要求。
- 所有平局决策最后以稳定 ID 决胜。
- 现有 UtilityBuiltin.GenerateEntityId 与表现 Entity、特效和异步 View 共用进程级序列，不能直接充当 LogicEntityId。
- LogicEntityIdAllocator 的 next value 属于权威状态，必须进入快照、回放和 Hash。

### 11.2 异步资源

逻辑出生不能发生在“资源刚好加载完成”的渲染帧：

1. 关卡开始前预加载逻辑必需资源。
2. SpawnCommand 指定 EffectiveFrame 和 EntityId。
3. View 未准备好时，逻辑实体仍按命令出生；可以暂时没有 View。
4. 缺失逻辑配置必须暂停时间线或失败，不能生成半初始化实体。
5. 异步回调只能创建/绑定 View，不能决定逻辑组件何时存在。

### 11.3 确定性随机数

- 使用项目内确定性 RNG，例如 PCG 或 XorShift，状态进入快照和 Hash。
- World、Entity、Combat、Spawn 使用独立子流，避免一个系统增加随机调用扰动其他系统。
- 表现随机数使用单独 Unity RNG，不得访问逻辑 RNG。
- 每个随机事件记录 StreamId 和调用原因，Debug 构建可追踪调用序列。
- Guid.NewGuid 不得作为 Buff、建筑或效果的逻辑身份。

## 12. Unity Physics、投射物与命中

### 12.1 物理降级为表现

Physics.Simulate 可以暂时保留，用于非权威 Rigidbody、Trigger 表现和诊断，但其结果不得：

- 修改 LogicTransform。
- 决定伤害、治疗或选择结果。
- 决定单位是否穿墙。
- 决定投射物是否命中。

### 12.2 CharacterController 迁移

过渡期采用 Shadow 模式：

- 逻辑定点求解产生 expectedPosition。
- CharacterController 在独立诊断对象或不回写逻辑的路径计算 actualPosition。
- 记录差值、碰撞物和场景位置。
- 正式切换后，View Transform 直接跟随逻辑位置，CharacterController 不参与权威阻挡。

严禁“先用定点结果，再让 CharacterController 修正并回写”，这仍然是双权威。

### 12.3 投射物和命中

完整回放还需要迁移：

- 投射物位置和速度使用定点 Tick。
- 高速投射物使用 swept segment/circle，不只检查终点。
- 命中候选按 TOI、TargetId 排序。
- Direct Attack、AoE、Cleave 和 Projectile 共用稳定目标排序与 DamageEvent。
- 旧 HitBox Trigger 资源和脚本直接移除；命中表现只消费逻辑命中结果，不保留可误用的第二套命中入口。
- 选点输入记录逻辑世界坐标或稳定目标 ID，不在回放时重新做摄像机射线。

## 13. 阶段检查点、确定性日志与状态 Hash

### 13.1 阶段检查点与确定性日志必须分开

产品功能只需要“返回本局任一阶段开始时”。它不提供随时录像重放、任意 Tick seek 或战斗中间态续跑。每次阶段入口的非作战持久状态事务提交后、该阶段标准战斗初始化前，生成一个不可变阶段检查点，按 StageId/PhaseEpoch 保留本局所需历史。

除非明确标注为产品功能，本文后续出现的“回放”均指开发/CI 的逐 Tick 确定性验证日志；面向玩家的恢复能力统一称为“阶段检查点”，核心数据只包含资源、建筑、科技、地图视野等非作战持久状态。产品侧无需保存或重放从旧阶段到目标阶段之间的过程录像，阶段检查点本身就是目标状态包。

检查点不连续录制 Tick，也不保存阶段内命令流。一个阶段只在上述入口屏障发布检查点；若保存失败，阶段历史不得出现半份记录。玩家可以选择本局任一已记录阶段，恢复该阶段开始时的非作战持久状态，并重新执行该阶段的标准战斗初始化，而不是重放从旧阶段到目标阶段之间的录像。

这里的“阶段开始”是唯一恢复粒度：检查点只回答“进入该阶段时应携带哪些跨阶段状态”，不回答“阶段内当时打到了哪里”。因此阶段内新出生/死亡的战斗单位、即时战斗数值和导航缓存即使属于逐 Tick authority，也不自动成为产品存档字段；只有明确需要跨阶段延续的数据才能加入检查点白名单。

阶段检查点采用显式白名单，至少包含：

- ProtocolVersion、Build/ContentHash、关卡 ID、StageId、PhaseEpoch 和阶段入口参数。
- 金币、人口、天数、阶段资源、生产储备等持久化经济数据。
- 建筑 StableId、类型、等级、阵营、定点格位、朝向和需要跨阶段保留的工作状态。
- 已解锁科技、可叠加科技层数、所属阵营及其稳定来源。
- 地图已探索/已揭示区域、永久标记和其他需要跨阶段保留的视野数据。
- 关卡永久开关、已完成目标、一次性奖励领取状态，以及重建上述对象所需的稳定 ID allocator 状态。

阶段检查点明确不包含：

- 单位当前 HP/位置/目标、攻击前后摇、Buff 剩余 Tick、弹药、投射物和待结算伤害。
- Flow world 中间构建态、path handle、tile/shared-goal cache、job queue、reservation 和碰撞 solver 暂存。
- 当前输入帧、暂停 Token、子弹时间、动画状态、粒子、音频和 Display 插值。

恢复必须作为新的阶段启动事务执行：先停止并清空当前战斗世界，再按检查点重建经济、建筑、科技、视野和永久关卡状态；随后从 authored navigation 与重建后的建筑障碍生成新的 Flow world，并按该阶段标准入口重新出生英雄/单位、初始化战斗和逻辑时间。不得尝试补跑检查点之后的旧 Tick，也不得把旧 Flow/job/cache 接回新世界。

开发/CI 的确定性日志是另一类产物，用于证明相同初始状态和命令得到相同逐 Tick Hash。它可以包含 ProtocolVersion、Build/ContentHash、LogicFrameRate、初始测试状态、每帧 LogicInputFrame、外部命令和分层 StateHash，但不构成产品“任意帧恢复”承诺。

### 13.2 规范化序列化

- 实体按 StableEntityId 排序。
- Buff、目标、障碍、job、事件和缓存按稳定键排序。
- 不序列化对象引用、HashCode、InstanceID、内存地址和表现字段。
- 定点数序列化 raw integer。
- Dictionary 必须先转稳定有序序列。
- 导航 job 进度会影响未来结果，必须进入开发/CI authority Hash；产品阶段检查点不序列化 job，而是在恢复事务中重建导航世界。

### 13.3 Hash 分层

建议同时生成：

- WorldHash：实体、属性、攻击、Buff 和 RNG。
- NavigationHash：世界版本、job、path、tile 和 reservation。
- MovementHash：位置、速度、碰撞 mask 和重叠状态。
- CombatHash：待提交和已提交事件。
- TimeScaleHash：BasePlaybackScale、BulletTimeScale、PauseTokenSet、活跃 Source 和 EffectiveFrame。
- FullHash：以上组合。

出现分叉时可以快速定位系统，而不是只有一个总 Hash。

### 13.4 回放工具

- 支持从第 0 帧纯输入重放。
- 支持加载某个阶段检查点并从该阶段标准入口重新开始。
- 首个 Hash 分叉立即停止并导出字段级 Diff。
- 导出前后若干帧输入、事件、RNG 调用和导航 job 日志。
- Headless runner 不创建 Animator、Camera 和 View。

## 15. 分阶段落地

### 阶段 A：确定性基线和观测

工作：

- 先修复或替换现有 Fix64，完成 LogicScalar 数学门禁。
- 定义 StableEntityId、LogicCommand、StateHash 和规范化序列化。
- 建立独立 LogicEntityIdAllocator，allocator state 进入快照和 Hash。
- 为当前系统记录逐帧输入、位置、攻击和导航 Hash。
- 加入禁用 Time/Stopwatch/InstanceID/UnityRandom 的逻辑域扫描规则。
- 保存现有典型战斗场景的输入日志和结果。

门禁：

- 数值库在 Mono、IL2CPP 和目标平台的 raw 结果一致。
- 算术黄金值、溢出、Sqrt、Normalize 和随机属性测试全部通过。
- 能定位当前系统在不同帧率下的首个分叉帧。
- 所有权威字段都有明确 owner 和序列化规则。

### 阶段 B：输入与攻击时间线

工作：

- 接入 RawInputEventQueue 和 LogicInputFrame。
- 回放模式禁用真实输入。
- 内容时长迁移为 TickCount。
- DirectAtkComp/MoveAtkComp 共用绝对帧 AttackSchedule。
- 建立 LogicTimeControlService、TimeScaleCommand、PauseControlCommand 和倍率分段输入 cutoff。
- 建立统一 AnimationRate Presenter，禁止业务直接覆盖 Animator.speed。

门禁：

- 120/60/30/15fps 与人工卡顿输入日志完全一致。
- 0.3/0.3/1.0 的自动攻击起手间隔为 30 Tick。
- 输入与攻击单元测试覆盖所有边界。
- 1、0.5、0.2 倍下逻辑事件流按 Tick 完全一致，区别仅是真实耗时。
- 子弹时间中动画速度与有效逻辑倍率同步，UI 和渲染帧率不变。

### 阶段 C：稳定 ID、生命周期与 RNG

工作：

- 替换逻辑中的 GetInstanceID、Guid 和 UnityRandom。
- 出生、销毁、障碍和投射物改为带 EffectiveFrame 的命令。
- View 异步加载与逻辑出生解耦。
- 索敌、目标列表和事件平局增加 StableEntityId。

门禁：

- 打乱资源完成顺序和 GameObject 创建顺序，Hash 不变。
- 相同种子重放 RNG 调用序列一致。

### 阶段 D：确定性导航 job

工作：

- Stopwatch 毫秒预算改固定工作量。
- integration cost、heap、job queue、cache eviction 增加稳定顺序。
- 禁止实体调用链同步构建。
- 关键世界启动前预热。

门禁：

- 注入不同 CPU 延迟和诊断开关，tile 完成帧一致。
- 相同导航命令的 NavigationHash 一致。

### 阶段 E：定点位置和静态碰撞 Shadow

工作：

- 引入 LogicTransform、LogicScalar 和定点静态碰撞。
- 现有 Flow/Controller 继续运行，但只记录差异。
- 建立墙、角落、窄道、薄墙、起始重叠场景集。

门禁：

- 新逻辑 solver 在所有 golden 场景结果稳定。
- Controller 差异可解释，且不回写逻辑。
- 性能达到预算后才切换权威位置。

### 阶段 F：单位避碰和动态障碍

工作：

- 帧初空间桶、MoveIntent、稳定 Pair solver、批量 Commit。
- 手动英雄和 AI 进入同一 collision solver。
- 建筑改为 authored LogicObstacle。
- Ghost、碰撞半径和特殊穿透改为逻辑 mask。

门禁：

- 交换实体注册顺序、容器顺序和 View 创建顺序，结果不变。
- 大规模重叠恢复、窄门对向流和建筑增删 Hash 一致。

### 阶段 G：移除 Unity 物理权威

工作：

- CharacterController 不再改变逻辑位置。
- Projectile、HitBox、AoE、Cleave 和 Selector 迁到定点查询。
- Physics Trigger 仅表现和诊断。

门禁：

- 关闭 Physics.Simulate 后，权威 FullHash 和伤害结果不变。
- Unity Layer Matrix 和 Collider 微调不改变逻辑回放。

### 阶段 H：跨平台回放门禁

工作：

- Windows Editor、Windows Player 和目标移动平台运行同一 replay corpus。
- 长局压力回放、阶段检查点恢复、字段级分叉报告。
- 固化 ProtocolVersion 和内容 Hash。

门禁：

- 全部平台逐 Tick FullHash 一致。
- 10 万 Tick 压力回放无分叉、NaN、溢出和未排序容器告警。

## 16. 双跑与切换策略

### 16.1 Shadow 原则

- 旧系统保持权威，新系统只计算 expected，不影响任何 Transform、目标或伤害。
- 每 Tick 比较 DesiredVelocity、ResolvedDisplacement、目标 ID、攻击边界和事件。
- 差异日志必须包含 frameId、entityId、输入帧、帧初状态、候选列表和最终平局键。
- Shadow 不能调用会改变旧系统容器、缓存或随机数的 API。
- 旧、新导航世界必须是两个独立实例，不能共用当前静态 Flow cache、job queue、world revision、bottleneck 或 scratch buffer。
- Shadow 输入必须是权威帧初状态的深只读视图；伤害、出生、事件、音效和 View 写入全部禁止。
- 旧 float 与新定点轨迹只比较玩法不变量和容差诊断；最终 bit-exact 门禁是新实现对新实现的 replay Hash。

### 16.2 切换原则

- 每个阶段只能有一个权威 writer。
- 不允许新 Flow + 旧 CharacterController 回写，也不允许旧 Flow + 新碰撞后再被 PhysX 修正。
- 切换通过明确 FeatureFlag 完成，并在关卡开始时固定，不能局中切换。
- 回滚 FeatureFlag 只影响下次开局；已有 replay 必须记录 flag/protocol。

## 17. 测试矩阵

### 17.1 调度和输入

- 15、30、60、120、无上限渲染帧率。
- 单渲染帧 0、1、2、15、300 个逻辑 Tick。
- 暂停、恢复、GameSpeed 切换。
- 按键边沿、held、同帧多事件、迟到事件。

### 17.2 攻击

- 所有 0 和边界 Tick 时长组合。
- 自动攻击、移动攻击、攻击中打断。
- 同帧互杀、目标死亡、目标离开射程、弹药耗尽。
- Buff 在起手前、命中前、命中帧、ReadyFrame 生效。
- 多目标顺序和 miss RNG。

### 17.3 寻路

- 同格目标、跨 sector、多 portal、窄门、不可达岛。
- tile pending、runtime dirty、cache eviction。
- 完全相同 cost 的 heap 平局。
- 改变容器插入顺序、资源加载顺序和 CPU 延迟。

### 17.4 静态碰撞

- 正撞墙、斜撞墙、沿墙滑动、内外角。
- 高速跨薄墙、极小位移、巨大位移。
- 起点合法、贴边、轻微穿透、深度穿透。

### 17.5 单位碰撞

- 两单位对撞、追尾、交叉和完全重叠。
- 一动一静、双方静止、Ghost、不同 collision mask。
- 英雄手动移动对 AI 群。
- 100、500、1000 单位密集出生和窄门通行。
- StableEntityId 顺序、注册顺序和对象池顺序全排列抽样。

### 17.6 回放

- 同进程重复 100 次。
- 不同渲染帧率和卡顿注入。
- 不同日志开关、性能统计开关。
- 每个阶段入口保存检查点，恢复后逐字段核对资源、建筑、科技、视野和永久关卡状态。
- 恢复必须清空战斗单位、攻击/Buff/投射物、Flow job/cache、输入、暂停和子弹时间瞬态，再按阶段入口重新初始化。
- 检查点序列化顺序、内容 Hash 和恢复结果不受 View/资源加载完成顺序影响。
- 跨平台 replay corpus。
- 首帧分叉字段级 Diff。

### 17.7 子弹时间

- 1、0.75、0.5、0.2 和最小允许倍率。
- 倍率在攻击起手、命中前一 Tick、命中 Tick、后摇和 ReadyFrame 切换。
- 倍率在移动、撞墙、单位重叠、Flow tile pending 和投射物飞行中切换。
- 同一 TimeScaleCommand 日志在 15、30、60、120fps 和卡顿追帧下产生相同逐 Tick FullHash。
- 验证逻辑 Tick 序列不变，真实 Tick 间隔按倍率变化，不能出现可变逻辑 deltaTime。
- 多来源子弹时间按 SourceId 添加、更新、删除，最强减速策略与移除顺序无关。
- LogicTicks 和 RealTime 两种持续时间分别验证，回放只依赖记录后的命令。
- 倍率切换不清 accumulator，不产生额外 Tick、丢 Tick或插值倒退。
- 子弹时间期间快速按键，所有边沿归帧且不丢失。
- 子弹时间中出生、对象池复用和切换 Animator Controller，动画倍率立即正确。
- 暂停与子弹时间嵌套：暂停不推进 Tick，恢复后继续原倍率，不产生 backlog。
- 两个以上 PauseToken 交错申请/释放，只有最后一个 Token 释放后才恢复。
- 暂停状态下 Resume 通过外部控制通道生效，不依赖 Logic Tick。
- 暂停前 accumulator 存在余量时，恢复后相位连续且不多跑/少跑 Tick。
- LogicTicks 子弹时间在暂停期间冻结；RealTime 子弹时间按记录的外部结束命令处理。
- 阶段检查点不保存子弹时间或暂停瞬态；恢复阶段按标准入口重新建立时间控制状态。

## 18. 性能原则

确定性不等于每 Tick 必须完成所有导航工作，但每 Tick 完成多少工作必须由整数配额决定。

- 逻辑帧仍不丢帧；性能不足会增加渲染延迟，但不能跳逻辑。
- 子弹时间会减少每真实秒执行的 Tick 数，但不能改变单 Tick 工作配额、碰撞迭代数或导航 job quota。
- 从低倍率恢复到 1 倍时不补跑“子弹时间期间少执行的 Tick”；那些 Tick 从未到期，不属于 backlog。
- 导航 job 配额以 operation count 表达，Stopwatch 只记录性能，不参与分支。
- 使用数组、稳定索引和对象池，避免每 Tick Dictionary 转排序列表。
- 帧初快照、空间桶和 pair buffer 复用内存。
- Hash 可以分层和分频，但 Debug/CI 必须支持逐 Tick FullHash。
- 超预算日志只能观测，不能提前结束逻辑求解。
- 极端追帧需要状态日志和 watchdog，但 watchdog 只能报错或暂停，不能丢 Tick。

## 20. Definition of Done

只有同时满足以下条件，才能宣布“逻辑时间精确、输入逐 Tick、不受渲染帧影响、全定点可回放”：

- 所有 gameplay duration 使用整数 Tick。
- 所有输入有 frameId，按键无丢失、无重复。
- 子弹时间只改变 Tick 调度速率，不改变固定 Tick 语义和业务 Deadline。
- TimeScaleCommand、PauseControlCommand、活跃倍率/暂停来源和合成结果进入开发/CI 回放与 Hash；产品阶段检查点不恢复这些战斗瞬态。
- 渲染帧率、UI 和输入泵不受子弹时间影响；Animator 通过统一 Presenter 同倍率减速。
- LogicScalar 数学库通过跨平台 raw 结果、溢出和属性测试。
- 权威位置、速度、导航、碰撞和攻击不使用 float。
- 导航 job 不使用墙钟预算。
- 所有权威遍历和平局有稳定键。
- 所有实体读取统一帧初快照并批量提交。
- CharacterController、PhysX、Collider 和 Trigger 不改变权威结果。
- 异步资源完成时机不改变逻辑出生帧。
- 逻辑 RNG 与表现 RNG 完全隔离。
- 开发/CI 回放包含完整外部命令、初始种子和内容版本。
- 产品阶段检查点只保存明确的非作战白名单，并能从本局任一已记录阶段入口原子重建资源、建筑、科技、视野和永久关卡状态。
- Windows 与目标平台运行标准 replay corpus，逐 Tick FullHash 一致。
- 10 万 Tick 压力测试无分叉、溢出、NaN 和状态残留。
