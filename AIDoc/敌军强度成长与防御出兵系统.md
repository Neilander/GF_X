# 敌军强度成长与防御出兵系统

## 1. 文档目的

本文冻结敌军强度成长、防御阶段出兵和据点守军的目标方案，作为数据迁移、运行时实现、编辑器改造和测试验收的唯一清单，避免在后续修改中退回旧的“每天手配数量与等级”方案。

本文中的“价值”默认指“以橙髓为单位的等价战力”。它不是实际掉落、扣除或建造支出，也不是单位数量；橙髓只是所有兵种、数量和等级之间统一可比较的计量单位。

## 2. 已确定的设计目标

### 2.1 关卡内敌军成长

- 进攻阶段的 LDtk 据点守军随当前天数成长。
- 防御阶段的敌方出兵随当前天数成长。
- 守军的成长速度低于防御出怪，二者不能使用同一条成长曲线。
- 两者共用兵种等级价值、非线性数量价值和小队构成求解算法。
- 每关只配置预期天数，不逐日配置目标强度。
- 预期天数位于成长曲线斜率最高处；超过预期天数后斜率快速下降，避免长期局继续高速膨胀。
- 初始强度和成长速度都可被开局 Tag 等运行时效果修改。
- 路线、出兵时间和小队启用日期保持可重复；当前据点、建筑或单位状态不能改变防御路线。

### 2.2 作者输入保持精简

每个单兵种小队只要求作者填写：

- 单位类型。
- 初始价值 `InitialStrengthValue`，单位为橙髓等价战力。
- 数量成长权重 `CountGrowthWeight`，范围 0 到 1。

`CountGrowthWeight=1` 偏向增加低等级单位数量，`CountGrowthWeight=0` 偏向减少数量并提高等级。算法最多生成两个相邻等级段，不允许作者逐日手配数量和等级。

### 2.3 单兵种模板

- 一个 LDtk Soldier 点只表示一个兵种。
- 一个防御小队模板只表示一个兵种。
- 同一路线可以配置多个不同兵种的小队模板。
- 防御小队模板直接参与运行时出怪，不生成按天的 `D几` 数据实例。
- 编辑器中不展示按天实例名；模板 ID 由路线名和可空后缀派生，只有后缀可编辑。

## 3. 橙髓价值标尺

### 3.1 军事建筑推导单位等级价值

从 `BuildingTable` 中找到 `Type=Army` 且 `UnitID` 对应目标兵种的军事建筑。

定义：

```text
P1 = Lv1Production
P2 = Lv2Production > 0 ? Lv2Production : P1
P3 = Lv3Production > 0 ? Lv3Production : P2

C1 = Lv1Cost
C2 = Lv1Cost + Lv2Cost
C3 = Lv1Cost + Lv2Cost + Lv3Cost

I1 = C1 / P1
I2 = C2 / P2
I3 = C3 / P3
```

`I1/I2/I3` 是每名兵的原始累计投入值，单位为橙髓。

由于高级军事建筑的性价比低于一级建筑，原始投入不能全部视为有效战力。最终供强度算法使用的等级价值为：

```text
V1 = I1
V2 = I2 * EnemyUnitLevel2ValueScale
V3 = I3 * EnemyUnitLevel3ValueScale
```

折减系数放在 `GameConfig`，初始建议值：

```text
EnemyUnitLevel2ValueScale = 0.90
EnemyUnitLevel3ValueScale = 0.75
```

这两个值必须大于 0 且不大于 1。折减后必须满足 `V1 < V2 < V3`；不满足时明确报错，不能排序、钳制或回退到原始投入值。

编辑器必须同时展示 `I1/I2/I3` 和 `V1/V2/V3`，让作者能直接判断高级兵折减是否合适。

### 3.2 数量价值为非线性

设小队总人数为 `n`，数量价值函数为 `Q(n)`。

少量单位阶段需要体现协同，价值略高于线性：

```text
n <= pivot:
Q(n) = n + synergy * n * (n - 1) / (2 * pivot)
```

超过拐点后，由于拥堵、单次伤害溢出和范围伤害，边际价值逐渐下降：

```text
n > pivot:
Q(n) = Q(pivot)
     + entrySlope * tailScale * (sqrt(1 + 2 * (n - pivot) / tailScale) - 1)
```

其中 `entrySlope = Q(pivot) - Q(pivot - 1)`。

共享配置：

```text
EnemyStrengthEarlyCountPivot
EnemyStrengthEarlyCountSynergy
EnemyStrengthCrowdingTailScale
```

`Q(n)` 必须始终单调递增；少量阶段人均价值提高，大量阶段边际价值低于拐点附近。

### 3.3 小队组合价值

对于总人数 `n`、各等级人数 `count[level]`：

```text
AverageUnitValue = sum(count[level] * V[level]) / n
CompositionValue = Q(n) * AverageUnitValue
```

`CompositionValue` 的单位仍是橙髓等价战力。LDtk 和防御表中的初始价值都使用这一标尺。

旧数量数据迁移为价值时，以旧小队原本的兵种、等级和数量计算 `CompositionValue`，以尽量保持迁移前的实际编成强度，而不是简单把旧数量原样写进价值字段。

## 4. 天数成长曲线

### 4.1 曲线形状

Day 1 是初始价值的基准点，倍率为运行时初始强度修正 `InitialStrengthScale`。

使用中心位于关卡 `ExpectedDays` 的单调 S 型曲线。当前确定性实现使用有理 sigmoid：

```text
S(x) = 0.5 + x / (2 * (1 + abs(x)))

EffectiveDay = 1 + (Day - 1) * GrowthSpeedScale
HalfWidth = max(1, (ExpectedDays - 1) * HalfWidthRatio)
FirstX = (1 - ExpectedDays) / HalfWidth
CurrentX = (EffectiveDay - ExpectedDays) / HalfWidth
Progress = clamp01((S(CurrentX) - S(FirstX)) / (1 - S(FirstX)))
FinalGrowth = ExpectedDays * GrowthPerExpectedDay
Multiplier = InitialStrengthScale * (1 + FinalGrowth * Progress)
TargetValue = InitialStrengthValue * Multiplier
```

性质：

- Day 1 不受成长速度修正影响，保证初始强度修正和成长速度修正职责分离。
- `ExpectedDays` 附近斜率最大。
- 预期天数越长，允许的最终成长总量越大。
- 超过预期天数后仍可增长，但边际增长迅速放缓。

### 4.2 守军与出怪使用不同曲线

共享公式，但配置分离：

```text
EnemyGarrisonStrengthGrowthPerExpectedDay
EnemyGarrisonStrengthGrowthHalfWidthRatio

EnemyDefenseStrengthGrowthPerExpectedDay
EnemyDefenseStrengthGrowthHalfWidthRatio
```

约束：

- 守军的主要增长速度必须低于防御出怪。
- 编辑器按同一 `ExpectedDays` 同图展示两条倍率曲线。
- 自动校验 Day 2 到 `ExpectedDays * 2` 范围内，守军倍率不能超过防御出怪倍率。
- 初始建议：守军每预期天增量 `0.10`，防御出怪每预期天增量 `0.18`；两条曲线半宽初始均为 `0.25`。最终值通过预览调校。

不使用“先算同一曲线再临时乘守军倍率”的实现，因为那会把初始差异、斜率差异和后期收敛混在一起，且无法独立预览和验证。

### 4.3 运行时效果接口

运行时效果按上下文提供：

```text
EnemyStrengthContext.Garrison
EnemyStrengthContext.DefenseWave

GetEnemyInitialStrengthScale(context)
GetEnemyGrowthSpeedScale(context)
```

现有 `LvTag_OverwhelmingForceI/II` 从“直接增加最终数量”迁移为初始强度倍率，避免在求解后再次修改人数。未来成长速度 Tag 通过同一接口返回倍率。

旧 `ModifyEnemySpawnCount` 必须删除全部调用，防止价值成长和数量成长叠加。

## 5. 给定价值求解小队构成

输入：

```text
InitialStrengthValue
CountGrowthWeight
Day
ExpectedDays
InitialStrengthScale
GrowthSpeedScale
V1/V2/V3
对应上下文的成长曲线配置
共享数量价值配置
```

步骤：

1. 计算当天 `TargetValue`。
2. 由最高等级价值求允许的最小数量价值，由一级价值求允许的最大数量价值。
3. 使用 `CountGrowthWeight` 在最小、最大数量价值之间插值，得到目标数量价值。
4. 对单调函数 `Q(n)` 二分求最近的整数人数。
5. 计算该人数下所需的平均单位等级价值。
6. 找到包围该平均值的两个相邻等级。
7. 用鸡兔同笼闭式解出高等级人数，其余为低等级人数，并做确定性四舍五入。

结果最多包含两个相邻等级段，例如 `Lv1 x 8 + Lv2 x 2`。不枚举所有数量与等级组合。

若目标价值低于一名一级单位、等级价值不严格递增、输入权重越界或人数超出明确上限，运行时直接报错，不静默跳过或 fallback。

## 6. 数据模型

### 6.1 LevelTable

新增：

```text
ExpectedDays int
```

每关填写预期通关天数。它控制该关成长曲线拐点和总成长幅度，不逐日填写目标强度。

### 6.2 LDtk Soldier 据点守军

字段：

```text
Identifier string             单位类型，不包含按天派生等级
StrengthValue float           初始橙髓等价战力，必须大于 0
CountGrowthWeight float       数量成长权重，范围 0..1
```

删除旧 `Count` 语义。Importer 必须严格读取 `StrengthValue` 和 `CountGrowthWeight`，转换为 `Fix64` raw 序列化到 `EntityPresetPoint`；字段缺失、非有限数、非正价值或权重越界均明确报错。

`EntityPresetPoint` 不直接序列化 `Fix64` 对象，保存：

```text
unitStrengthValueRaw long
unitCountGrowthWeightRaw long
```

并通过属性和严格 setter 暴露 `Fix64`。

### 6.3 DefendAttackGroupTable 防御小队模板

目标列：

```text
Identifier
LevelIdentifier
ActiveDays int[]
RouteIdentifier
UnitIdentifier
InitialStrengthValue Fix64
CountGrowthWeight Fix64
AfterGroupIdentifier
StartDelaySeconds Fix64
ExpectedEngagementSeconds Fix64
Suffix
```

关键语义：

- `InitialStrengthValue` 单位为橙髓等价战力，替代旧数量。
- `ActiveDays` 是模板在哪些真实天数启用，不创建每日实例。
- `UnitIdentifier` 是单一兵种，不含等级。
- 路线已在模板内，不重复配置路线信息。
- `AfterGroupIdentifier` 引用同一天也处于启用状态的模板，否则明确报错。
- `Identifier` 由 `RouteIdentifier + 可空 Suffix` 派生，同关卡不可重复。

## 7. 运行时链路

### 7.1 进攻阶段据点守军

`PhaseManager.ConfigureInvadeSpawnPoints` 保存：

```text
Position
UnitType
AuthoredStrengthValue
CountGrowthWeight
Name
```

不再保存作者配置的单位等级和数量。

进入进攻阶段生成守军时：

1. 读取当前真实天数。
2. 读取当前关卡 `ExpectedDays`。
3. 从军事建筑推导该兵种 `I1/I2/I3` 和折减后的 `V1/V2/V3`。
4. 读取守军成长曲线、共享数量参数和 Tag 修正。
5. 求解为一个或两个等级段。
6. 每个等级段分别生成确定性的 `InvadeSpawnPlan`。
7. 玩家已占领据点仍按既有逻辑不生成守军；据点归属不会改变其他据点的强度或路线。

### 7.2 防御阶段出怪

防御阶段按当前真实天数筛选 `ActiveDays.Contains(day)` 的模板，不再维护“配置轮次上限 + 复用最后一天 + 无限数量倍率”。

每个启用模板：

1. 使用防御出怪曲线计算当天目标价值。
2. 求解该单兵种模板的等级与数量构成。
3. 沿模板已有路线建立出怪候选。
4. 保留既有固定出兵窗口、全波错峰、预计接战时间反推临时移速、进入首个玩家据点视野后恢复移速的链路。

出兵时间仍由全波次统一排程固定下来；生成单位时只消费已经求解好的计划，不实时重复计算路径和价值。

防御阶段开始前必须完成流场距离预热和出怪计划构建，预热未完成不能出怪。

## 8. 防御配置编辑器

入口保持在 Unity 顶层菜单：

```text
Tools/Defense Route Editor
```

### 8.1 编辑方式

- 顶部选择关卡和预览天数。
- 路线编辑继续按稳定的传送点 ID 记录与预览。
- 出兵组页展示当前关卡所有可复用模板。
- 每个模板在当前预览天数提供“当天启用”勾选框，直接维护 `ActiveDays`。
- 不展示或生成 `D几` 实例。
- 仅编辑模板后缀，ID 自动由路线名和后缀刷新。

### 8.2 单模板预览

每个模板显示：

- 初始价值与当天目标价值，单位均为橙髓。
- 原始投入 `I1/I2/I3`。
- 折减后的有效等级价值 `V1/V2/V3`。
- 当天成长倍率及 Tag 修正后的倍率。
- 求解结果，例如 `Lv1 x N + Lv2 x M`。
- 实际组合价值、目标价值和离散误差。
- 总人数和平均等级。

### 8.3 曲线与合理性判断

展示 Day 1 到 `ExpectedDays * 2`：

- 守军倍率曲线。
- 防御出怪倍率曲线。
- 当前模板每天的目标价值、总人数和平均等级。

自动给出现象级提示：

- 两条曲线是否都在预期天数附近达到最大斜率。
- 预期天数后边际增长是否明显下降。
- 守军曲线是否始终慢于防御出怪曲线。
- 离散组合价值与目标价值误差是否过大。
- 预期天数内是否出现异常高等级或异常数量。
- 作者期望的怪海模板在短关卡内是否过早升到三级。
- 精英模板在预期天数内是否过早增长到过多单位。

编辑器预览与运行时必须调用同一个 `Fix64` 求解器，不能另写近似公式。

```text
EnemyDefenseStrengthGrowthHalfWidthRatio = 0.25
```

等级性价比：

```text

```

```text

EnemyStrengthEarlyCountSynergy = 0.45

```

旧的通用成长参数在迁移完成后删除，避免运行时存在两套权威配置。旧防御无限成长参数若已无其他用途也一并从来源表删除。

## 10. 确定性与性能要求

- 核心成长、价值、构成和排程均使用 `Fix64`。
- 同一关卡、天数、Tag、表数据和据点归属必须得到完全相同的构成、路线、出兵时间和临时移速。
- 不根据玩家当前建筑、单位视野或临时单位位置改变防御路线。
- 据点占领可按既有规则减少对应守军或出兵来源，这是可重复策略的一部分。
- 强度构成在阶段准备时一次性求解；单位生成时不重复推导。
- 路径距离使用现有流场距离预热链路；预热完成事件驱动出兵准备，不每帧轮询路径。

## 11. 错误处理

以下情况必须明确报错并阻止错误计划运行：

- 军事建筑或兵种映射不存在。
- 军事建筑成本、兵力无效。
- 高级兵折减后价值不严格递增。
- `ExpectedDays <= 0`。
- 初始价值非正。
- 数量权重不在 0 到 1。
- LDtk 新字段缺失或仍使用旧 `Count`。
- 当前日启用模板引用未启用的前置模板。
- 目标价值不足以生成一名一级单位。
- 固定出兵窗口、路线或预热结果无效。

不通过静默跳过、默认值或 fallback 隐藏配置错误。

## 13. 验收标准

1. 同一 Soldier 或防御模板只需配置兵种、初始橙髓价值和数量权重，即可在不同天得到确定性构成。
2. 同一天相同初始价值下，守军成长倍率低于防御出怪倍率。
3. Day 1 调整成长速度不改变初始强度；调整初始强度立即改变 Day 1 目标价值。
4. 高等级兵价值由对应军事建筑推导，且折减系数实际影响最终构成。
5. 怪海权重产生更多、更低等级单位；精英权重产生更少、更高等级单位。
6. 数量少时价值超过线性，大量拥堵后边际价值下降但总价值仍单调增长。
7. 防御编辑器能在保存前看见两条曲线、每日构成和误差，并能直接判断参数是否导致过早三级或数量失控。
8. 防御阶段不再依赖逐日小队实例，路线与出兵时间不会因玩家当前建筑或单位状态改变。
9. 流场预热未完成时不会提前出怪；预热完成后生成链路无明显阶段切换卡顿。
10. 所有异常数据产生带关卡、模板或 Soldier 标识的明确错误，不静默降级。

## 14. 实现与验证记录

### 14.1 真实天数语义修正

`ActiveDays` 使用全局真实 Day，不是“第几次防御”。`Lv2`、`Lv3` 和 `LvTest` 从 `BuildBeforeInvade` 开局，第一次进入 `BuildBeforeDefend` 前会先将 Day 1 推进为 Day 2，因此这三关首场防御使用的 10 个模板统一配置为 `ActiveDays=2`。`Lv1` 教程首战不走该表，现有模板保持 `2,3,4`。

该规则已加入永久回归测试 `DefendRouteRuntimeTests.FirstDefenseGroupsUseRealDayTwoForBuildBeforeInvadeLevels`，防止以后把“防御轮次”再次混入真实天数配置。

### 14.4 Launch 现象验证边界

实际从 `Launch` 场景通过 procedure 进入 `Lv2` 后，已观察到：

- 新价值算法在进攻阶段生成 37 名守军。

完整防御实机出怪链路尚未得到一次有效的端到端现象验证。此前临时测试 Runner 在 37 个守军的异步视图绑定完成前强制切阶段，触发既有实体生命周期错误，属于测试入口制造的伪故障，不能用来判断强度系统成败。该 Runner 和结果文件已删除；后续实机验证必须等待 presentation 绑定完成，或使用无视图的权威逻辑测试链路。
