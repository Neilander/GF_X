## 性能完成目标

性能目标按最终二倍速的 `60` 逻辑 Tick/s 和后期负载制定，不能以当前 Lv2 单场景“比旧版本快”作为完成条件。

1. `16.67ms` 是二倍速下整个游戏主线程每帧的硬上限，不是 Flow 导航可独占预算。为给渲染、战斗、UI 及性能较弱设备保留余量，当前参考机 Unity Editor 同入口验收要求：`LogicFrameTick P99 <= 8.33ms`、单 Tick `<= 16.67ms`；其中 Flow 导航队列与寻路工作合计 `P99 <= 4ms`、单 Tick `<= 8ms`。任何 `20ms` 级 Flow 或逻辑峰都明确判定为未完成。
2. 必须增加后期规模门禁：导航面积至少为 Lv2 的 `4` 倍且同屏至少 `100` 个移动单位，覆盖同目标合并与多目标并发。高层 path request、tile integrator 和 dynamic rebuild 的每 Tick 工作必须受各自 operation quota 严格限制；主线程峰值不得随地图总格数或同目标 source 数线性增长。
3. 时间切片不能只把尖峰换成不可接受的等待。压力门禁同时记录 request 首次可用延迟、P95/P99 和最大 pending Tick；同目标新增 source 应复用既有目标侧结果，不得因同组 source 数量增长而让整组原子等待线性放大。
4. 毫秒阈值用于当前参考机回归和弱机余量代理；架构验收以复杂度、quota 上界和规模曲线为主。未来有明确最低配置硬件后，再在同入口补最低配置实测，不能反向放宽上述架构门禁。

## 已锁定的核心差异与冻结方案

改造前，项目虽然在 NavigationSync 先 collect 单位请求，但仍逐 source 同步执行 `EnsurePathHandle -> reverse hierarchy/downward customization -> PathHandle materialization`。共享 policy 容器不等于原文的一个多 source path request；同 Tick 多兵接敌仍把全部高层查询压在一个逻辑 Tick。这是本轮已锁定并已实施修改的架构差异，后续验收不得退回热点函数式补丁。

正式方案是唯一的、有状态的多 source portal path request 层，当前代码已按以下边界实现：

1. Collect 阶段只提交 source、agent type、moving-target identity、Fix64 raw goal 和最大行程。
2. Resolve 阶段先解析每组唯一的权威 stable goal、goal sector、source island 与 touched hierarchy versions；combat slot 只保留为 final local binding。
3. 同一 `(world, agent type, moving target/stable goal, source island)` 形成一个 request job。目标侧 connector/reverse policy 只初始化一次。
4. 首个 source 建 route tree，后续 source 只做 merging/start connector；heap pop、edge relax、connector 和 witness 展开都计入确定性 operation quota，job 可跨 Tick 恢复。
5. request 完整后原子提交所有 PathHandle，再提交 portal-window demand；moving-target 的精确 final tile 仅在单位已到最终 sector 且对 per-source binding 的确定性 LOS 被阻断时提交。中间状态必须进入 Navigation authority digest。
6. 项目禁止旧目标作为当前 authority，因此 job 未完成时是显式 `PendingNavigation`：prepared MoveIntent 只读并输出零速，不同步补完、不读旧 handle/旧方向、不走直线 fallback。
7. moving target 同 sector 换格不重建高层 route，只更新 local binding；终点 LOS 内按 23.6.2 忽略 flow tile 并直接 steering，阻挡时才构建 exact final tile。跨 sector 只失效必要 suffix/层级，动态障碍只按 dirty version 更新受影响拓扑与作业。
