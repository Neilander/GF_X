架构 Brain 双接口设计

IControlBrain 定义了所有 Brain 的输出信号：移动方向 Move、攻击 Attack、技能 Skill1/2/3。不管是玩家手动操控还是 AI 自动操控，下游组件（MoveComp、AtkComp）都只看这个接口。

ITickBrain 是 AI 专用的扩展——需要每帧被调用 Tick() 来更新决策。玩家的 PlayerBrain 不需要实现它，因为输入来自手指/摇杆。

这种策略模式让 Entity 不关心"谁在控制我"，只管读取 Brain 接口的值。

② 状态枚举与配置参数
public class SoldierAIBrain : IControlBrain, ITickBrain
{
    public enum SoldierState
    {
        Idle,     // 站着不动，等待玩家靠近
        Follow,   // 跟随玩家，自然散开
        Combat    // 发现敌人，散开交战
    }

    // --- 配置参数 ---
    public float RecruitRadius = 8f;        // 玩家多近时开始跟随
    public float FollowDistanceMin = 2.5f;  // 跟随最近距离
    public float FollowDistanceMax = 5f;    // 跟随最远距离
    public float WeaponRange = 1.5f;        // 武器攻击距离
    public float DetectEnemyRange = 10f;    // 发现敌人的距离
    public float SeparationRadius = 1.5f;   // 同阵营分离半径
    public float SeparationWeight = 1.5f;   // 分离力权重
    public float AvoidPlayerRadius = 2.5f;  // 避让玩家半径
    public float AvoidPlayerStrength = 3f;  // 避让玩家力度
    public float SeekWeight = 0.6f;         // 趋向力权重
    public float LeashRange = 15f;          // 脱离战斗回到跟随

参数 三态状态机 + 调参旋钮

状态机极简：Idle → Follow → Combat，只有三个状态。这比行为树简单得多，但对小兵来说足够了。

参数分两类：

  • 距离阈值：RecruitRadius（招募距离）、LeashRange（拴绳距离）控制状态切换
  • 力场权重：SeparationWeight、AvoidPlayerStrength、SeekWeight 控制移动时各种力的混合比例

注意这些参数现在是写死的默认值，不是从 ScriptableObject 读取的。实际上 LJ 力场参数已经移到了 GroupMoveManager 的 Inspector 面板上，这里的 SeparationRadius 等字段部分是历史遗留，实际生效的是协调器里的配置。

注入 构造后惰性注入

SoldierAIBrain 是纯 C# 对象（不是 MonoBehaviour），所以不能用 Unity 的 [SerializeField] 或 Inspector 来注入依赖。

Inject() 在 BrainFactory.Create() 中调用，把两个关键依赖塞进来：

  • _player — 玩家实体引用，用来计算跟随距离
  • _allEntities — 全局实体列表，用来自己找敌人

技能全部硬编码 false —— 小兵不释放技能，只有 Move 和 Attack 两个输出信号会被修改。

_joinedGroup 标记是否已经把玩家注册为协调器中的"领袖"，只做一次。

④ 主循环 Tick — 每帧决策入口
public void Tick(IEntityContext self, float dt)
{
    Move = Vector2.zero;
    Attack = false;
    _desiredMoveDir = Vector3.zero;

    if (!self.Alive) return;

    // 惰性刷新
    if (_player == null || !_player.Alive)
        _player = EntityRegistry.Player;
    if (_allEntities == null || _allEntities.Count == 0)
        _allEntities = EntityRegistry.AllEntities;

    // 惰性标记领袖
    if (!_joinedGroup && _player != null && _player.Alive
        && GroupMoveManager.HasInstance)
    {
        int leaderId = (_player as MAEntity)?.GetInstanceID()
            ?? _player.GetHashCode();
        GroupMoveManager.Instance.Coordinator.SetAgentLeader(leaderId, true);
        _joinedGroup = true;
    }

    // 同步索敌范围给 TargetComp
    if (self.TargetComp != null)
        self.TargetComp.AggroRange = DetectEnemyRange;

    SyncTargetComp(self);
    UpdateState(self);

    switch (State)
    {
        case SoldierState.Idle:   TickIdle(self, dt);   break;
        case SoldierState.Follow: TickFollow(self, dt); break;
        case SoldierState.Combat: TickCombat(self, dt); break;
    }
}

核心 Tick 主循环结构

每帧执行一次，流程清晰：

  • 重置输出 — 每帧开头把 Move 和 Attack 清零，避免上一帧的值残留
  • 存活检查 — 死了就什么都不做
  • 惰性刷新 — 如果玩家引用丢了（死亡/重生），从 EntityRegistry 重新拿。这是防御性编程，因为 Inject 只在创建时调用一次
  • 领袖注册 — 首次 Tick 时把玩家标记为 LJ 力场的"领袖"节点，这样协调器知道谁是中心
  • 同步索敌 — 把 Brain 的 DetectEnemyRange 写进 TargetComp，保持一致
  • 状态机 — 先更新状态转换，再执行当前状态的逻辑

注意 UpdateState 在 TickXxx 之前调用——这意味着状态转换和状态执行在同一帧完成，没有一帧延迟。

⑤ 状态机转换 UpdateState
private void UpdateState(IEntityContext self)
{
    switch (State)
    {
        case SoldierState.Idle:
            // 有敌人 → 直接进 Combat
            if (self.TargetComp?.CurrentTarget != null)
                State = SoldierState.Combat;
            // 同阵营领袖在附近 → Follow
            else if (_player != null && _player.Alive
                     && self.Side == _player.Side)
            {
                if (HorizontalDist(self.Position, _player.Position)
                    <= RecruitRadius)
                    State = SoldierState.Follow;
            }
            break;

        case SoldierState.Follow:
            if (self.TargetComp?.CurrentTarget != null)
                State = SoldierState.Combat;
            break;

        case SoldierState.Combat:
            var enemy = self.TargetComp?.CurrentTarget;
            if (enemy == null)
                State = SoldierState.Follow;
            else if (_player != null && _player.Alive
                && HorizontalDist(self.Position, _player.Position)
                   > LeashRange)
                State = SoldierState.Follow;
            break;
    }
}

核心 状态转换规则

转换逻辑一目了然：

Idle →

  • 有敌人？→ 直接 Combat（优先级最高）
  • 同阵营玩家在 RecruitRadius(8m) 内？→ Follow
  • 注意 self.Side == _player.Side 这个检查——敌方小兵不会跟随玩家，只有同阵营的才会

Follow →

  • 发现敌人？→ Combat
  • 注意：Follow 状态下不会回到 Idle，一旦招募就永远跟着（除非战斗）

Combat →

  • 敌人死了/消失？→ 回 Follow
  • 离玩家超过 LeashRange(15m)？→ 回 Follow（拴绳机制，不让小兵追太远）

注意 没有 Combat → Idle 的路径。小兵一旦被招募，战斗结束后回 Follow 而不是 Idle。

设计 空方法的意义

空函数不是偷懒——这是一个有意的设计决策。

之前的版本在 Idle 状态也算了 separation 力来推开重叠的单位，但这导致小兵站着的时候不停抖动（"抽搐"）。现在 Idle 就是什么都不做，重叠问题交给物理碰撞体自然处理。

⑦ TickFollow — 跟随玩家
private void TickFollow(IEntityContext self, float dt)
{
    if (_player == null || !_player.Alive) return;

    float speed = self.GetProperty(
        CreatureMainProperty.Speed);
    Move = Vector2.zero;

    // Follow 不需要自己算方向，提交零速度
    // 协调器的 LJ 吸引力会自然拉向领袖
    SubmitToCoordinator(self, Vector3.zero, speed);
}

核心 零速度的魔法

这是整个设计最精妙的地方：Follow 状态提交零期望速度。

为什么不自己算追踪方向？因为 GroupMoveCoordinator 用 Lennard-Jones 势场模型统一处理所有 agent 的位置关系：

  • 离领袖太远 → LJ 吸引力把你拉过去
  • 离领袖太近 → LJ 斥力推你出去
  • 同伴太近 → 同阵营斥力推开

Brain 只需要说"我没有自己想去的方向"，协调器就会算出一个让群体自然散开、跟随领袖的合力。这比手写 follow + separation + avoidance 简洁太多了。

⑧ TickCombat — 战斗逻辑
private float GetEffectiveAttackRange()
{
    float enemyEqR = GroupMoveManager.HasInstance
        ? GroupMoveManager.Instance.Coordinator
            .EnemyEquilibriumRadius
        : 1.5f;
    return enemyEqR + WeaponRange;
}

private void TickCombat(IEntityContext self, float dt)
{
    Vector3 myPos = self.Position;
    var enemy = self.TargetComp?.CurrentTarget;
    if (enemy == null || !enemy.Alive) return;

    float distToEnemy = HorizontalDist(myPos, enemy.Position);
    float speed = self.GetProperty(
        CreatureMainProperty.Speed);
    float effectiveRange = GetEffectiveAttackRange();

    if (distToEnemy <= effectiveRange)
    {
        // 在攻击范围内 → 攻击
        Attack = true;
        Move = Vector2.zero;
        SubmitToCoordinator(self, Vector3.zero, speed);
    }
    else
    {
        // 追敌：NavMesh 寻路
        Move = Vector2.zero;
        self.MoveComp.MoveTo(enemy.Position);

        // LJ 力叠加到 External
        SubmitCombatLJ(self, speed);
    }
}

核心 双层移动架构

攻击距离计算：effectiveRange = 敌对斥力平衡半径 + 武器射程。这意味着士兵会被 LJ 斥力推到平衡距离外，而武器射程刚好能从那个位置打到敌人。物理和逻辑完美配合。

战斗移动是双层的：

  • 在范围内：停下来打。提交零速度给协调器，让 LJ 力处理堆叠推开（多个小兵围殴一个敌人时不会叠在一起）
  • 在范围外：用 MoveComp.MoveTo() 走 NavMesh 寻路到敌人位置，同时 SubmitCombatLJ 把 LJ 力叠加到 MoveExecutor.AddExternal()——这不会覆盖 NavMesh 路径，而是在路径基础上叠加一个推力

关键 追敌时 Move 始终是零！小兵不通过 IControlBrain.Move 信号移动，而是直接调用 MoveComp.MoveTo()。这绕过了标准的输入管线。

⑨ 协调器提交 — SubmitToCoordinator / SubmitCombatLJ / ApplyVelocity
/// Combat 追敌时：NavMesh 负责寻路，LJ 力叠加防堆叠
private void SubmitCombatLJ(IEntityContext self, float speed)
{
    if (!GroupMoveManager.HasInstance) return;
    var coordinator = GroupMoveManager.Instance.Coordinator;
    int agentId = (self as MAEntity)?.GetInstanceID()
        ?? self.GetHashCode();

    coordinator.SubmitDesiredVelocity(agentId, Vector3.zero,
        safeVel => {
            if (safeVel.sqrMagnitude > 0.01f)
                self.MoveExecutor.AddExternal(safeVel);
        });
}

/// 向协调器提交期望速度，回调中执行 MoveTo
private void SubmitToCoordinator(IEntityContext self,
    Vector3 desiredVelocity, float speed)
{
    if (!GroupMoveManager.HasInstance) return;
    var coordinator = GroupMoveManager.Instance.Coordinator;
    int agentId = (self as MAEntity)?.GetInstanceID()
        ?? self.GetHashCode();

    coordinator.SubmitDesiredVelocity(agentId, desiredVelocity,
        safeVel => { ApplyVelocity(self, safeVel, speed); });
}

private void ApplyVelocity(IEntityContext self,
    Vector3 velocity, float speed)
{
    if (velocity.sqrMagnitude < 0.001f)
    {
        self.MoveComp.StopMove();
        return;
    }
    Vector3 myPos = self.Position;
    Move = Vector2.zero;
    self.MoveComp.MoveTo(myPos
        + velocity.normalized * speed * 0.1f);
}

架构 协调器回调模式

两个 Submit 方法的区别很关键：

SubmitToCoordinator（Follow 用）：

  • 提交期望速度 → 协调器算出安全速度 → 回调中用 ApplyVelocity 执行 MoveTo
  • 安全速度 = 期望速度 + LJ 力的合成结果

SubmitCombatLJ（Combat 追敌用）：

  • 提交零期望速度 → 协调器只返回 LJ 力 → 用 AddExternal 叠加到移动执行器
  • 不覆盖 NavMesh 路径，只是额外加一个推力防止堆叠

ApplyVelocity：

  • 力太小（< 0.001）就停止移动，避免微抖
  • speed * 0.1f 是把目标点设在前方很近的地方（0.1秒的距离），这样 NavMesh 只走一小步就会重新计算，跟随更平滑
⑩ SyncTargetComp — Brain 自主索敌
private void SyncTargetComp(IEntityContext self)
{
    if (self.TargetComp == null || _allEntities == null)
        return;

    // 已有活着的目标，不覆盖
    if (self.TargetComp.CurrentTarget != null
        && self.TargetComp.CurrentTarget.Alive)
        return;

    // Brain 自己遍历找最近敌人
    IEntityContext nearest = null;
    float nearestDist = DetectEnemyRange;

    for (int i = 0; i < _allEntities.Count; i++)
    {
        var other = _allEntities[i];
        if (other == self || !other.Alive) continue;
        if (other.Side == self.Side
            || other.Side == SideType.NoSide) continue;

        float dist = HorizontalDist(
            self.Position, other.Position);
        if (dist < nearestDist)
        {
            nearestDist = dist;
            nearest = other;
        }
    }

    if (nearest != null)
        self.TargetComp.CurrentTarget = nearest;
}

private static float HorizontalDist(Vector3 a, Vector3 b)
{
    float dx = a.x - b.x;
    float dz = a.z - b.z;
    return Mathf.Sqrt(dx * dx + dz * dz);
}

核心 双重索敌保障

为什么 Brain 要自己找敌人？因为 TargetComp 自己的扫描可能漏掉（注释里也写了）。这是一个冗余机制：

  • 如果 TargetComp 已经有活着的目标 → 不覆盖，尊重它的选择
  • 只在目标为空或已死时，Brain 才自己遍历全局列表找最近敌人

过滤规则：

  • 跳过自己
  • 跳过死亡单位
  • 跳过同阵营（Side 相同）
  • 跳过中立单位（NoSide）

HorizontalDist 只算 X-Z 平面距离，忽略 Y 轴高度差——这对平面战斗游戏是对的，不会因为站在斜坡上就算错距离。

性能 每帧遍历所有实体是 O(n) 的。如果战场上有几百个单位，这里可能成为瓶颈。但对于当前规模（几十个小兵）完全够用。

⑪ BrainFactory — 工厂创建与注入
// BrainFactory.cs
public static class BrainFactory
{
    public static IControlBrain Create(
        BrainType tp, MAEntity entity,
        EntityParams p)
    {
        switch (tp)
        {
            case BrainType.Player:
                return new PlayerBrain();

            // 注意：这个现在没有使用！
            case BrainType.EnemyAI:
                return new EnemyAIBrain();

            // 注意：这个现在没有使用！
            case BrainType.FriendlyAI:
                return new FriendlyAIBrain();

            case BrainType.SoldierAI:
                var soldierBrain = new SoldierAIBrain();
                soldierBrain.Inject(
                    EntityRegistry.Player,
                    EntityRegistry.AllEntities);
                return soldierBrain;

            default:
                return new PlayerBrain();
        }
    }
}

工厂 创建 + 即时注入

BrainFactory 是简单工厂模式，根据 BrainType 枚举创建对应的 Brain 实例。

SoldierAI 是唯一需要 Inject 的 Brain 类型——因为它需要知道玩家是谁、场上有哪些实体。其他 Brain（PlayerBrain、EnemyAIBrain）不需要这些依赖。

注意 EnemyAIBrain 和 FriendlyAIBrain 注释标了"现在没有使用"。当前所有 AI 小兵（不管友方敌方）都用 SoldierAIBrain，通过 Side 属性区分阵营行为。

注入时机在 Create 里立即执行，但 Brain 在 Tick 中还有惰性刷新逻辑兜底——万一 EntityRegistry.Player 在创建时还没准备好，后续帧会自动补上。
